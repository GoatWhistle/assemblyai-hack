### КРИТИЧНО: дозировка — поле грязное

Число и единица **разнесены по двум колонкам**, и оба поля для комбинированных препаратов содержат список через `;`:

```
SUB='AMOXICILLIN; CLAVULANIC ACID'   STR='200; 28.5'   UNIT='mg/5mL; mg/5mL'
SUB='ZINC OXIDE; DIMETHICONE'        STR='2; 2.1'      UNIT='g/100g; g/100g'
SUB='CEFAZOLIN SODIUM'               STR='225'         UNIT='mg/mL'
SUB='POLYMYXIN B SULFATE'            STR='500000'      UNIT='[iU]/1'
SUB='CEFUROXIME SODIUM'              STR='750'         UNIT='mg/8mL'
```

Замеренные цифры:

- **23 024 строки (19,8 %)** содержат `;` в дозировке — то есть наивный `float()` падает на каждой пятой строке.
- **2 442 строки (2,1 %)** — дозировка пустая.
- Распределение числа компонентов: 1 → 90 774; 2 → 10 573; 3 → 4 273; 4 → 3 513; 5 → 880; … **максимум 102 компонента** (аллергенные смеси).
- **10 923 строки** имеют компонент в виде `.75`, `.8`, `.05` — ведущий ноль отсутствует. Это валидно для `float()` в Python, но сломает наивную regex `\d+\.\d+`.
- Хорошая новость: **рассогласований количества компонентов между `STRENGTH` и `UNIT` — 0**. Списки всегда параллельны, `zip()` безопасен.
- Единица — это дробь с знаменателем (`mg/1`, `mg/5mL`, `mg/8mL`, `g/100g`, `[iU]/1`, `[hp_C]/1`). Знаменатель `/1` значит «на единицу формы» (таблетка). Топ: `mg/1` (47 930), `mg/mL` (12 873), `mg/g` (6 464), `g/100g` (5 973).
- `[hp_C]`, `[hp_X]`, `[hp_M]` — **гомеопатические разведения** (4 063 + 2 599 + 842 ≈ 7 500 строк). Это не лекарства в клиническом смысле.

Вывод по дозировке: единое парсящееся поле — **нет**. Нужен парсер «split по `;` → zip с единицами → разбор числителя/знаменателя». Это ~25-40 строк кода, не 5.

### Дубликаты (name, strength, form, route)

**Да, и их катастрофически много.**

## Допущение 2 — список ISMP LASA машинно-парсится

Оба PDF скачались без авторизации: `ISMP_ConfusedDrugNames_2023.pdf` — 631 964 байта, 14 страниц, PDF 1.4; `ISMP_ErrorProneAbbreviation_List.pdf` — 330 358 байт, 8 страниц, PDF 1.6.

### Текст или скан?

**Текстовый слой есть, это не скан.** `pdftotext` извлекает 33 789 символов в raw-режиме. OCR не нужен — это снимает главный риск.

### Но режим извлечения решает всё

Раскладка — **таблица из 4 колонок** (две пары «Drug Name | Confused Drug Name» рядом). С `-layout` колонки перемешиваются, партнёры отрываются от названий:

```
          Drug Name            Confused Drug Name                  Drug Name
              Abelcet               amphotericin B                  ALfentanil*               Confused Drug Name
             Accupril                    Aciphex                                                     SUFentanil*
                                   acetaZOLAMIDE                      Alkeran                          Leukeran
        acetaminophen              acetaminophen                      Alkeran                           Myleran
```

Видно, что `ALfentanil*` и `SUFentanil*` оказались на разных строках, а `acetaZOLAMIDE` висит без пары. Парсить это — действительно полдня боли.

**Решение найдено: `pdftotext -table`.** Тот же файл, другой ключ:

```
Drug Name                Confused Drug Name              Drug Name             Confused Drug Name
Abelcet                  amphotericin B                  ALfentanil*           SUFentanil*
Accupril                 Aciphex                         Alkeran               Leukeran
acetaminophen            acetaZOLAMIDE                   Alkeran               Myleran
acetaZOLAMIDE            acetaminophen                   Allegra               Viagra
```

Пары встают на одну строку, разделитель надёжный — **2+ пробела**. Раскладка проверена на стр. 2, 6 и последней — стабильна по всему документу. Ключ `-table` есть в Xpdf 4.00, который уже установлен.

Распределение по числу ячеек в строках данных: **4 ячейки — 510 строк**, 3 — 41, 2 — 11, 1 — 47. То есть 510 строк дают по 2 пары каждая.

### Сколько пар и какого размера парсер

Реально написанный и запущенный парсер (**~30 строк** Python: skip-лист шапок + `re.split(r'\s{2,}')` + сборка пар) дал:

- 1 072 сырых кандидата → **1 061 уникальная пара** после лёгкого фильтра.

Но в выдаче есть мусор — перенос скобочных уточнений на следующую строку склеивает несвязанные записи:

```
('menthol)', 'nicardipine')
('menthol)', 'nizatidine')
('recombinant)', 'tuberculin purified protein')
```

**41 строка** из 510 содержит такой «хвост» с непарной скобкой (всего 98 строк данных содержат `(`). Отбросив все ячейки со скобками, получаем **960 чистых пар**. Это приемлемая потеря: скобочные записи — это уточнения вида «Kaopectate (bismuth subsalicylate)», их и так нельзя произнести в рецепте однозначно.

Итог: парсер LASA — **30-40 строк**, а не 200, и не полдня. Ручная транскрипция 30 пар **не нужна и была бы хуже** (см. Допущение 1 → набор ниже).

### Список сокращений — другая история

`-table` на abbreviations даёт 390 непустых строк, из них **только 93 с 4+ ячейками**, а **231 строка односоставная** — текст переносится внутри узких колонок. Извлекается ~99 записей-кандидатов, но поля тихо съезжают между записями:

```
['l',        'Liter',      'Lowercase letter l mistaken', 'Use L (UPPERCASE) for liter']
['ml',       'Milliliter', 'as the number 1',             'Use mL (lowercase m,']
['MM or M',  'Million',    'Mistaken as thousand',        'Use million']
```

В строке `ml` поле «Misinterpretation» содержит `as the number 1` — это **продолжение предыдущей записи**, а не смысл для `ml`. Такое склеивание молча портит данные, и заметить его можно только вручную. Плюс в тексте есть потерянные глифы (кинжал `†` извлёкся как пустота, `©` как `�`).

Здесь **ручная выписка выгоднее**: записей всего ~99, клинически релевантных (U/IU/cc/µg/q.d./OD/MS/ноль в конце) — **20-30**, и они меняются раз в несколько лет. 30-40 минут вручную против ~3 часов на парсер с валидацией.

**ПОДТВЕРЖДЕНО для LASA** (текстовый PDF + `pdftotext -table` → 960 чистых пар, парсер ~35 строк, ≈1 ч).
**ЛОМАЕТСЯ для сокращений: многострочные ячейки съезжают между записями, парсер даёт тихо испорченные поля — эти ~25 записей выписать руками (0,5 ч), не парсить.**

## Допущение 4 — синтетическое аудио с известным ground truth

### AssemblyAI TTS — нет

По документации Voice Agents озвучка существует только как часть живой сессии агента (`"voice": {"voice_id": "anna"}`). **Отдельного standalone TTS-эндпоинта нет**: нельзя послать текст и получить WAV-файл. Использовать AssemblyAI для генерации тестового корпуса не получится — и это к лучшему, иначе мы тестировали бы распознаватель на аудио того же вендора.

### Что реально брать

| Вариант | Лицензия | Проверено | Годность |
|---|---|---|---|
| **edge-tts** 7.2.8 | нет в метаданных PyPI (обёртка к сервису Microsoft) | есть на PyPI | Лучшее качество и много акцентов бесплатно, **но это сетевой вызов недокументированного API Edge — не оффлайн и юридически серая зона для демо** |

Рекомендация: **Kokoro основной + edge-tts для разнообразия акцентов**.

### Телефонное качество — команды проверены на этой машине

Базовая цепочка 8 кГц / µ-law (`ffmpeg` 9.0), проверено `ffprobe` → `codec_name=pcm_mulaw, sample_rate=8000`:

```bash
ffmpeg -y -i clean.wav -ar 8000 -ac 1 -c:a pcm_mulaw phone.wav
```

Полная цепочка с полосой телефонного канала (добавляет срез частот, которого одна передискретизация не даёт):

```bash
ffmpeg -y -i clean.wav \
  -af "highpass=f=300,lowpass=f=3400,acompressor=threshold=-18dB:ratio=3,alimiter=limit=0.95,aresample=8000" \
  -ac 1 -c:a pcm_mulaw phone.wav
```

### Шум с контролируемым SNR — здесь план сломался бы молча

Наивный `amix` с угаданным `volume` **не даёт заданный SNR**. У меня замер показал `mean_volume` −21,1 дБ и до, и после микширования: шум был на 20 дБ ниже сигнала и просто не сдвинул среднее. Если так собрать корпус, все файлы окажутся с одинаковым фактическим SNR, а метрика «устойчивость к шуму» будет фикцией.

Правильно — **измерять уровни и вычислять усиление**, а не угадывать:

```bash
#!/bin/bash
# mix_snr <speech.wav> <noise.wav> <target_snr_db> <out.wav>
S=$1; N=$2; SNR=$3; OUT=$4
rms(){ ffmpeg -i "$1" -af volumedetect -f null - 2>&1 \
       | sed -n 's/.*mean_volume: \(-*[0-9.]*\) dB.*/\1/p'; }
SR=$(rms "$S"); NR=$(rms "$N")
GAIN=$(python -c "print(f'{($SR)-($NR)-($SNR):.3f}')")
ffmpeg -y -i "$S" -i "$N" -filter_complex \
  "[1:a]volume=${GAIN}dB[n];[0:a][n]amix=inputs=2:duration=shortest:normalize=0,\
   alimiter=limit=0.95,aresample=8000[m]" \
  -map "[m]" -ac 1 -c:a pcm_mulaw "$OUT" -loglevel error
```

Проверено на трёх целевых SNR — усиление считается корректно и монотонно, клиппинга нет:

| Цель SNR | Усиление шума | max_volume |
|---|---|---|
| 20 дБ | +0,100 дБ | −15,7 дБ |
| 10 дБ | +10,100 дБ | −11,9 дБ |
| 5 дБ | +15,100 дБ | −9,2 дБ |

Два обязательных момента: `normalize=0` в `amix` (иначе ffmpeg сам делит громкость на число входов и ломает расчёт) и `alimiter` (без него на низких SNR получается `max_volume: 0.0 dB`, то есть клиппинг — я это воспроизвёл).

Источник шума без внешних файлов: `ffmpeg -f lavfi -i "anoisesrc=d=10:c=pink:a=0.05"`. Для правдоподобия лучше реальный больничный/офисный фон — но тогда нужен CC0-источник (Freesound), это отдельная задача на ~0,5 ч.

### НЮАНС, который надо назвать вслух: TTS-метрика меряет не то

Если синтезировать речь TTS и считать по ней Entity Error Rate, мы измеряем **связку «этот TTS → этот ASR», а не точность на человеческой речи**. Искажение системное, а не шум, и работает в обе стороны:

1. **Смещение вверх (главное).** TTS выдаёт идеальную артикуляцию, стабильный темп, отсутствие дизартрии, акцента, покашливания, ложных старт-стопов и наложения речи. Реальный EER на живых звонках будет **заметно хуже** нашего.
2. **Смещение вниз, локальное.** TTS часто **неправильно произносит** редкие препараты и латынь по буквенным правилам (чего врач не делает). Тогда ASR наказывается за ошибку синтезатора. Особенно это бьёт по LASA-парам — то есть по самому важному для нас месту.
3. **Общая G2P-модель.** Если TTS и ASR опираются на схожие корпуса и правила «буквы → звуки», ошибки коррелируют, и цифра получается оптимистичной по причинам, не связанным с качеством ASR.

Итог: **абсолютное значение EER на TTS-аудио публиковать как «точность системы» нельзя.** Что корректно:

- использовать как **регрессионную и сравнительную** метрику: конфигурация A против B, с keyterms против без, чистое против 8 кГц. Здесь синтетическая природа сокращается при сравнении и выводы остаются валидными;
- фиксировать **дельту**, а не абсолют: «keyterms снижают EER на LASA-парах с X до Y на одном и том же корпусе»;
- обязательно вручную проверить произношение отобранных препаратов в синтезе — иначе п.2 незаметно испортит именно adversarial-подмножество;
- честная формулировка для сдачи: *«Корпус синтезирован TTS (Kokoro/edge-tts), 8 кГц µ-law, SNR 5/10/20 дБ. Абсолютный EER не переносится на человеческую речь: синтез не содержит акцентов, дизартрии и перекрытия речи, а на редких названиях сам произносит их по буквенным правилам. Метрика применяется только для сравнения конфигураций на одинаковом аудио. Валидация на реальной речи не проводилась.»*

### Есть ли бесплатный корпус живой речи с названиями препаратов

Да, но **не по-английски** — это ключевое ограничение:

- **PxCorpus / PxSLU** (французский) — 1 981 запись, 55 говорящих (38 % не-специалисты, 25 % врачи), 4 часа, рецепты, ручная транскрипция + семантическая разметка, **CC BY-4.0**. Единственный полностью открытый корпус именно произнесённых рецептов.
- **ADMEDVOICE** (польский) — ~15 часов, 28 говорящих, включает названия препаратов и болезней, есть шумные записи.
- **APmed** (французский) — 320 текстовых отчётов, не аудио.

Готового открытого англоязычного корпуса с произнесёнными названиями лекарств **не нашлось**. Практичный компромисс на хакатоне: записать **10-20 фраз своим голосом** (и голосами участников) по тем же скриптам, что у TTS, и показать EER на этой мини-выборке рядом с синтетической. Это не статистика, но это честное доказательство, что система работает на живой речи, и снимает главное возражение судей. Цена — ~1 ч.

**ЛОМАЕТСЯ: план говорит «сгенерировать корпус», но (а) у AssemblyAI нет standalone TTS, (б) Piper не MIT, а GPL-3.0, (в) наивный amix не даёт заданный SNR и портит корпус молча, (г) EER на TTS-аудио нельзя выдавать за точность на человеческой речи, а открытого англоязычного корпуса живой речи с препаратами нет.**

### Исправить фактические ошибки

1. **«116 155 продуктов» → 116 240** (на 15.09.2026), и файл обновляется ежедневно. Не хардкодить число в тестах, проверять порядок (`> 100_000`).
2. **«Piper (local, MIT)» → Piper GPL-3.0.** Основным сделать **Kokoro-82M (Apache-2.0)**.
3. **«23 пары FDA» → 23 строки таблицы = 22 группы**, из них 20 настоящих пар и 2 одиночные записи.
4. Убрать из плана идею брать TTS у AssemblyAI — такого API нет.

### Добавить шаги, которых в плане нет

5. **Фильтр `PRODUCTTYPENAME == 'HUMAN PRESCRIPTION DRUG'`** перед всем остальным: 116 240 → 56 619 строк, 3 730 названий, 2 573 вещества. Без него в keyterms попадут `alcohol`, `oxygen` и 7 500 гомеопатических разведений.
6. **Дедупликация по (name, strength, form, route)** — 80 % строк в Rx-подмножестве дубликаты (11 319 уникальных ключей из 56 619). Любая частотная статистика без этого меряет число дженериков.
7. **Нормализация солей.** Обнаружено при интеграции: `SUBSTANCENAME` хранит соль (`tramadol hydrochloride`, `vincristine sulfate`), поэтому `tramadol`, `hydralazine`, `hydroxyzine`, `trazodone`, `vinblastine`, `dobutamine` **не находятся** прямым сравнением. Нужен стриппер ~40 суффиксов. Эффект замерен: сходимость LASA-пар с каталогом **42,0 % → 52,3 %**.
8. **Keyterms не влезают целиком.** 2 573 Rx-вещества против лимита ~1 000 терминов — превышение в 2,6×. Нужен **частотно-ранжированный шортлист** (топ-N по числу продуктов) плюс принудительное включение всех LASA/tall-man названий. Это проектное решение, а не «выгрузить каталог».
9. **Adversarial-набор надо отбирать, а не импортировать.** Из 960 чистых LASA-пар обе стороны присутствуют в Rx-каталоге лишь у **240 пар** (после нормализации солей и симметричной дедупликации). Остальные — снятые с рынка бренды (Abelcet, Accupril, Advicor, Alkeran, Altocor), которых в NDC уже нет. Тестировать на них бессмысленно: система не обязана знать несуществующий препарат.

   Топ-пары по рыночному присутствию — готовый тест-сет: `lamotrigine↔levetiracetam`, `lamotrigine↔levothyroxine`, `olanzapine↔quetiapine`, `duloxetine↔fluoxetine`, `metformin↔metronidazole`, `clonazepam↔lorazepam`, `bupropion↔buspirone`, `alprazolam↔clonazepam`, `risperidone↔ropinirole`, `diazepam↔diltiazem`, `atomoxetine↔atorvastatin`, `carbamazepine↔oxcarbazepine`, `hydrocodone↔oxycodone`, `metoprolol succinate↔metoprolol tartrate`, `citalopram↔escitalopram`, `tramadol↔trazodone`, `glipizide↔glyburide`, `hydralazine↔hydrochlorothiazide`.
10. **Сокращения ISMP — выписать руками** (~25 записей, 0,5 ч), не парсить.
11. **`mix_snr` с измерением уровней** (скрипт выше) вместо угаданного `volume`. Обязательны `normalize=0` и `alimiter`.
12. **Записать 10-20 фраз живым голосом** как sanity-check к синтетическому корпусу.
13. **Раздел про ограничения метрики** в сдаточных материалах (формулировка выше).
