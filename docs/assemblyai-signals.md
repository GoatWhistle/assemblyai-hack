## 1. Entity Error Rate вместо WER

Главный аргумент AssemblyAI: WER считает все слова равными, но в транзакционном разговоре важны имена, номера счетов, даты и названия лекарств. Пропущенная цифра в номере рецепта ломает всю операцию, но на WER это 5% ошибки — почти незаметно.

Их собственные цифры на открытом бенчмарке Pipecat:

| Модель | Entity Error Rate | WER |
|---|---|---|
| Universal-3.5 Pro Realtime | 15,31% | 6,99% |
| Deepgram Flux | 50,50% | 15,58% |

Расхождение по сущностям в 3 раза против 2 раз по WER. Формулировка из статьи: модель, которая пропускает половину именованных сущностей в разговоре, всё ещё показывает WER, который выглядит защитимо.

Разбивка ошибок по типам: имена собственные — 16,92%, места — 6,28%, телефоны — 3,55%.

### Эффект накопления по ходу разговора

Самая сильная мысль статьи. При точности захвата сущностей 84,69% за один ход бронирование приёма из пяти ходов проходит успешно только в **43,6%** случаев. На моделях с меньшей точностью — 3%.

И дальше — то, что превращается в архитектурное требование: **шаги подтверждения ловят ошибку в 70% случаев и поднимают успех пятиходового сценария с 43,6% до 79,1%**.

### Что повышает точность (по данным AssemblyAI)

| Приём | Эффект |
|---|---|
| Promptability (доменный контекст) | −43% ошибок на медицинских терминах |
| Keyterms (до 100 строк, обновляемы на ходу) | Буст на конкретных названиях, бесплатно |
| Agent Context (передать текущий вопрос) | −10,2% WER |
| Context Carryover (предыдущие ходы) | Улучшение на последующих ходах |
| Шаги подтверждения | Ловят 70% ошибок |

### Рекомендованная ими методология оценки

1. Взять 200 своих собственных звонков, где сущности важны
2. Прогнать через обе сравниваемые модели
3. Посчитать промахи руками — «занимает один день»
4. Считать по ходам, содержащим сущности, а не по всем ходам
5. Требовать прозрачности методологии: размер набора, часы, разбивка по датасетам, а не одна усреднённая цифра

Прямое предупреждение в статье: не верить вендорам, которые дают одно число и никакого списка датасетов.

## 2. Observability: что мерить в продакшне

Четыре семейства сигналов.

**Латентность** (P50, P95, P99 — не средние):
- time to complete transcript (шлюз для LLM)
- LLM time-to-first-token
- TTS time-to-first-byte

**Прокси точности:**
- word-level confidence из streaming-сообщений
- entity capture rate на критичных для сценария токенах
- **caller repeat rate** — как часто пользователь повторяет одну и ту же фразу

**Метрики разговора:** barge-in rate, escalation rate, task completion rate, turns-to-resolution.

**Стоимость:** cost per completed task, не cost per hour, плюс учёт billable idle time на WebSocket.

### Фундаментальный тезис

> Голосовой агент — это цепочка, и LLM никак не может узнать, что его вход был неверным.

Когда STT ошибается (RX-7704132 слышится как RX-770 for 132), модель уверенно действует на испорченных данных. Это невидимо, если транскрипт не логируется.

Отсюда прямое архитектурное следствие: **каскадный пайплайн (отдельные STT→LLM→TTS) отлаживается, а чёрный ящик audio-in/audio-out не даёт увидеть ошибку распознавания без ручного просмотра.**

Это важно: 25 из 45 конкурентов взяли именно чёрный ящик Voice Agent API. AssemblyAI сама говорит, что для отладки нужен каскад.

### Caller repeat rate — самый дешёвый сигнал

Не нужна разметка, не нужен ревьюер, не нужно менять пайплайн. Нормализовать осторожно (пунктуацию заменять пробелами, а не удалять). Сегментировать по предшествующему вопросу агента, чтобы найти горячие точки: например, 19% повторов на запросе email против 1% на да/нет-подтверждениях.

### Коды закрытия WebSocket, которые надо логировать

| Код | Значение |
|---|---|
| 3007 | Некорректные аудио-чанки |
| 3008 | Достигнут трёхчасовой лимит (утечка биллинга) |
| 3009 | Превышен лимит сессий |

Логировать Error frame, а не обрезанную причину закрытия.

### Пороги алертов (их рекомендации)

- repeat rate: +2 пункта неделя к неделе
- barge-in rate: +5 пунктов неделя к неделе
- P95 time-to-first-audio: выше 1500 мс в течение 5 минут
- любое появление кодов 3008 или 3009

### Важно: в Voice Agent API это уже есть

Сессии Voice Agent API уже содержат timeline-артефакты: транскрипты пользователя, confidence-оценки, `time_to_first_audio_ms`, тайминги tool call (`duration_ms`, `dispatched_at_ms`), статус barge-in. AssemblyAI даёт Python-скрипт, считающий базовые метрики без дополнительной инструментации.

То есть построить честную панель метрик — это не недели работы, а разбор того, что API уже отдаёт. И этого не сделал никто.

## 3. Load testing: цифры и лимиты

**Целевые пороги:**
- finalization delay: < 500 мс на P95
- LLM time-to-first-token: низкие сотни мс
- TTS time-to-first-byte: < 300 мс
- end-to-end: < 1 секунды (там, где разговор перестаёт напоминать плохую телефонную связь)

**Что ломается первым, в порядке:** установка соединения при всплеске, очередь на LLM, backpressure у TTS, round-trip вызовов инструментов. Точность STT при этом стабильна — деградацию даёт реальное аудио (8 kHz телефония, шум, перебивания).

**Лимиты AssemblyAI:**
- Новых сессий в минуту: 5 (free) → 100+ (paid), автомасштабирование на 10% при утилизации выше 70%
- Жёсткого потолка конкурентности нет
- Превышение — close code 3009, «Unauthorized Connection: Too many concurrent sessions»
- Биллинг по длительности WebSocket, не по объёму аудио; **idle-время тарифицируется**
- Автоотключение сессии через 3 часа

**Ловушки биллинга:** неправильно закрытые сессии держатся 30 секунд (Voice Agent API) или 3 часа (streaming). Тест из тысячи звонков без аккуратной очистки может выставить счёт за 8+ часов, которых не было.

**Технические гейты:** аудио-чанки 50–1000 мс, иначе close code 3007. Отправлять аудио в реальном времени — быстрее закрывает соединение. Для телефонии `encoding="pcm_mulaw"`, по умолчанию ожидается 16-bit PCM. Явное завершение: `disconnect(terminate=True)` для streaming, `session.end` для Voice Agent API.

**Корпус для тестов — 50 худших звонков:** 8 kHz mulaw телефония (не студийное аудио), много сущностей, реальные акценты и фон, перебивания и фальстарты. Ground truth выверять руками — люди систематически теряют слова-заполнители и путают имена собственные.

**Ретраить только:** `at_capacity`, `concurrency_exceeded`, `internal_error`.

## 4. Code-switching: конкретика Universal-3.5 Pro

Архитектурно — никакого шлюза детекции языка. Все языки обрабатываются одной моделью в одном прямом проходе, без штрафа по латентности и без сбоев маршрутизации при переключении посреди фразы.

**18 языков в streaming** с code-switching: английский, испанский, французский, немецкий, итальянский, португальский, арабский, датский, нидерландский, финский, иврит, хинди, японский, китайский, норвежский, шведский, турецкий, вьетнамский. Для предзаписанного аудио — 99 языков через фолбэк на Universal-2.

```
wss://streaming.assemblyai.com/v3/ws
speech_model: "universal-3-5-pro"   # singular на streaming
language_codes: ["en", "es"]         # это смещение (bias), а не фильтр
```

Тонкость: `speech_model` (единственное число) на streaming против `speech_models` (множественное) на предзаписанном. `language_codes` направляет, но не блокирует неожидаемые языки.

**Цифры:** −22% относительного WER на code-switched аудио, плюс ещё 4% при подаче промптов. Латентность: медиана time-to-final **285 мс**, P95 374 мс, P99 443 мс — детекция языка не добавляет накладных расходов.

**Цена:** $0,45/час для всех 18 языков, keyterms prompting (100 терминов, обновляемы посреди стрима) — бесплатно.

Статья прямо критикует конкурентов на маршрутизации через детекцию языка: они катастрофически ломаются на переключении посреди высказывания, тогда как унифицированная архитектура держит хинглиш и подобную смешанную речь.

## Как это превращается в преимущество на хакатоне

Сопоставим то, что AssemblyAI объявила важным, с тем, что сделало поле (данные из [06-assemblyai-feature-usage.md](assemblyai-feature-usage.md)):

| Что AssemblyAI считает признаком зрелости | Сколько конкурентов это сделали |
|---|---|
| Entity Error Rate как метрика | 0 |
| Caller repeat rate | 0 |
| P50/P95/P99 разбивка латентности по компонентам | 0 (есть общие заявления «под 300 мс» без методологии) |
| Логирование close codes 3007/3008/3009 | 0 |
| Нагрузочное тестирование с профилями | 0 |
| Шаги подтверждения против накопления ошибок | Частично: claim-intake-agent, Saakshi, Voice Action Gate |
| Keyterms / promptability | Единицы |
| Code-switching как несущая функция | 1 полноценно (Saakshi, хинглиш) |
| Каскадный пайплайн для отлаживаемости | ~10 (остальные — чёрный ящик) |

**Вывод.** Есть готовая, опубликованная самой AssemblyAI рамка того, как выглядит правильно сделанный голосовой агент, и поле её игнорирует. Проект, который встроит эту рамку в продукт — не как раздел в README, а как работающую функциональность — попадёт точно в критерий «Application of Technology» в том виде, в каком его понимают судьи от AssemblyAI.

Конкретно это означает три вещи:

1. **Мерить Entity Error Rate на своём корпусе и показывать цифру** — с методологией, размером набора и разбивкой. Ровно так, как они требуют от вендоров.
2. **Встроить confirmation-контур** там, где сущность критична, и показать замером, как он поднимает успех многоходового сценария (их числа: 43,6% → 79,1%).
3. **Отдать наблюдаемость как часть продукта** — панель с P95 латентности по компонентам, caller repeat rate, entity capture rate, close codes. Это то, что Forward Deployed Engineer из AssemblyAI узнает мгновенно.

Детальная проработка этого в [09-strategy.md](strategy.md).
