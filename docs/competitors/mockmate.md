**1. Что построено**

Голосовой тренажёр собеседований: выбираешь роль (SDE / Data / PM / Behavioral), персону интервьюера (Friendly Coach / FAANG Bar Raiser / HR Screen), уровень, голос и длительность — и говоришь. Агент задаёт вопросы, оценивает каждый ответ 1-10 в реальном времени через function tools, считает филлеры / WPM / talk time из потока транскрипта, а в конце выдаёт report card: балл /100, hire-сигнал, разбор по вопросам, сильные стороны, зоны роста, экспорт в PDF и локальная история с дельтами («▲ +8 vs last attempt»).

**2. Как использован AssemblyAI**

Самое **детальное по фичам** использование Voice Agent API, с таблицей «фича → файл», и она длиннее, чем у кого-либо:

- временные токены `GET /v1/token` (`server.py`);
- **inline `session.update`** — вся конфигурация сессии одним сообщением при коннекте: system prompt под роль/персону/уровень, greeting, голос, keyterms, tools (`app.js → buildInlineSession()`);
- **client-side function tools с JSON-Schema**: `plan_interview`, `log_question`, `score_answer`, `end_interview`, через `tool.call` / `tool.result` (`tools.js`, `app.js`) — агент буквально управляет интерфейсом;
- PCM16 @ 24 kHz `input.audio` / `reply.audio`;
- **semantic turn-taking + barge-in** с флашем аудио по `input.speech.started`;
- **keyterms** биасинг под роль + **авто-извлечение из резюме** (`config.js → extractKeyterms()`, «60-term tech lexicon»);
- **`transcription_prompt`** (role-aware STT bias) — редкая фича, её почти никто не использует;
- **`language_codes`** для Hinglish code-switching (заявлено «18-language recognition»);
- **11 голосов** с persona-matched гендерно-консистентными дефолтами (`config.js → VOICES`);
- **`session.resume`** при обрыве соединения (`app.js → onSocketClosed()`);
- **`reply.create` + `conversation.message`** для end-early flow (`app.js → requestEnd()`);
- **word-level agent captions** через `transcript.agent.delta`.

Модель STT прямо не названа (нет «Universal-3»/«3.5» в README) — единственный пробел в иначе исчерпывающей таблице.

**3. Архитектура и стек**

Бэкенд `server.py` — **только стандартная библиотека Python, никакого pip**: раздаёт статику и минтит короткоживущие Voice Agent токены, держа ключ на сервере. Фронт — vanilla JS без зависимостей, разложенный по ответственностям: `config.js` (роли, персоны, keyterms, промпт), `tools.js` (4 tool-схемы + хендлеры), `coach.js` (аналитика филлеров/WPM + сборка отчёта), `audio.js` (захват + PCM-плеер + barge-in), `pcm-worklet.js` (AudioWorklet: Float32 → 24 kHz PCM16), `demo.js` (скриптованный демо-режим), `app.js` (WebSocket-протокол, экраны, HUD). CSS включает print-stylesheet для PDF-отчёта. Деплой — Render blueprint (`render.yaml`), free tier, «first load may take ~30s to wake up». Персистентность — только localStorage (история отчётов).

**4. Настоящая инженерная суть**

Реально нетривиальны четыре вещи:

(а) **Агент как драйвер UI через tool calling.** Это не декоративный tool call: `plan_interview` / `log_question` / `score_answer` / `end_interview` синхронизируют состояние LLM с состоянием приложения — question tracker, HUD, report card заполняются структурированными вызовами модели, а не парсингом её прозы. Правильная архитектура агентного приложения и лучшая демонстрация Voice Agent API среди разобранных.

(б) **Аудио-путь сделан руками и с пониманием**: AudioWorklet с ресемплингом в 24 kHz PCM16, «gapless playback scheduler with barge-in flush» — очередь воспроизведения, которую надо корректно сбросить в момент перебивания. Классический источник артефактов (обрывки фразы агента после barge-in), и здесь он решён явно.

(в) **Гибрид LLM-суждения и детерминированной аналитики**: филлеры и WPM считаются на клиенте из потока транскрипта, а не запрашиваются у модели. Как у Officer Parker, но MockMate делает это *live*, во время разговора, с выводом вердикта («Crisp» / «Too many fillers» / «Fast — slow down»).

(г) **`session.resume` на обрыве** — единственный проект здесь, который вообще думает про сетевую устойчивость разговора.

Плюс два продуктово-инженерных хода: **резюме → keyterms** (CV становится словарём для биасинга STT, одновременно продуктовая фича и рост точности на именах технологий) и **demo mode** — скриптованное полное интервью, работающее офлайн без ключа и микрофона («exercises the complete UI pipeline»). Второе — прямая страховка от провала на записи видео и на стенде судьи.

Что обёртка: сам «скоринг» — это промпт; никакой калибровки hire-сигнала нет, /100 берётся из LLM.

**5. Метрики и доказательства**

**Тестов нет ни одного** — ни pytest, ни JS-тестов, ни smoke-скрипта. Замеров латентности нет. Точность распознавания не измерена. Цифры в README — параметры, не измерения: 4 роли, 3 персоны, 4 function tools, 11 голосов, 18 языков распознавания, «60-term tech lexicon», оценки 1-10 и /100, «~30s to wake up» на free tier. Заявление «$250/hr coach for the cost of an API call» — маркетинг без unit-экономики (ни цены за минуту, ни средней длины сессии). Дельты истории («▲ +8 vs last attempt») сравнивают LLM-баллы, то есть шумный сигнал без доказанной воспроизводимости — два прогона одного ответа могут дать разный балл, и это нигде не проверено. Есть `docs/DEMO_VIDEO_SCRIPT.md`, `docs/SUBMISSION_CHECKLIST.md`, `docs/GET_YOUR_KEY.md` и питч-дек по `/slides.html`: подготовка к судейству сильная, доказательная база пустая.

**6. Сильные стороны**

Лучшее соотношение «глубина Voice Agent API / объём кода» среди разобранных: 11 задействованных фич, включая редкие (`transcription_prompt`, `session.resume`, `reply.create`, `transcript.agent.delta`, word-level captions). Ноль зависимостей на обеих сторонах — судья запускает `python server.py` на Python 3.9+, без pip и без npm; очень сильный аргумент по воспроизводимости. Презентация продумана до конца: live orb, стриминговые субтитры, event-stream консоль, анимированный report card, PDF через print-stylesheet, скриптованный demo mode для безупречного видео, встроенные слайды. В README есть **собственная таблица по критериям судейства** — они буквально написали за судью его оценочный лист. Продуктовые дифференциаторы (résumé-aware drilling, Hinglish, история с дельтами) конкретны и демонстрабельны.

**7. Слабые места и уязвимости**

- **Ноль тестов и ноль измерений** при 7 коммитах. Всё заявленное про качество («scored live», «hire signal», «delivery analytics») недоказуемо.
- **Скоринг не калиброван.** «Hire/no-hire signal» и /100 — выход LLM без валидации против реальных исходов найма. Судья с опытом найма спросит «чем подтверждено, что балл 78 значит что-нибудь?» — ответа нет. Officer Parker ровно этот риск осознал и сознательно демотировал общий балл в футер; MockMate, наоборот, ставит его в центр.
- **История с дельтами усиливает проблему**: сравнение двух некалиброванных LLM-баллов подаётся как измерение прогресса. Без test-retest проверки это может быть чистый шум, продаваемый как метрика.
- **Ниша перегружена.** Interview-coach — самая переполненная категория; прямой конкурент среди разобранных (Officer Parker) имеет более острый и менее воспроизводимый инсайт. MockMate — качественная реализация стандартной идеи; по Originality это слабейший его критерий, а «агент управляет приложением через tool calls» — про технику, не про продукт.
- **Client-side tools** (в отличие от server-side у Siberia) живут в браузере: состояние скоринга можно подделать. Для тренажёра не критично, но инженер отметит.
- **Free-tier Render**: «first load may take ~30s to wake up» — судья с большой вероятностью увидит холодный старт и решит, что демо мёртвое.
- Модель STT не названа — единственная строчка, отсутствующая в иначе полной таблице AssemblyAI.
- Нет серверной персистентности (только localStorage) — истории между устройствами нет, бизнес-аргумент про измеримый прогресс держится на одном браузере.
- Нет видео на момент сбора данных.
- Заявленный Hinglish-режим ничем не подтверждён: ни примера транскрипта, ни замера на code-switched речи.

**8. Чем это можно побить**

Их сила — покрытие фич; их дырка — **отсутствие доказательств и некалиброванный скоринг**.

Ход 1: **калибровка как фича.** Показать test-retest: один и тот же записанный ответ прогоняется N раз, разброс балла публикуется. Если наша метрика детерминирована (или её разброс измерен и мал) — мы обесцениваем их «▲ +8 vs last attempt» одним слайдом, потому что их дельта может быть меньше собственного шума.

Ход 2: **замеры латентности разговора** (p50/p95 end-of-turn → первый аудиосэмпл и время до срабатывания barge-in flush). Они реализовали barge-in и gapless-плеер — сложные штуки — но не измерили. Числа тут дешёвы и убийственны.

Ход 3: **server-side tools + серверная персистентность.** Перенести исполнение инструментов на сервер (как Siberia) и хранить историю в БД: закрывает подделку состояния и даёт настоящий cross-device прогресс, которого они честно не имеют.

Ход 4: **уйти из их ниши или увести её вглубь.** Если мы тоже в coaching — брать измеримый исход (не «hire signal», а объективный проверяемый показатель, например доля ответов, покрывающих структуру STAR, посчитанная детерминированно). Общая эвристика: против их 11 фич выставлять не 12 фич, а 5 фич + 5 замеров.
