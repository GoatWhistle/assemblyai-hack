# Saakshi — Consent You Can Prove

**Тир:** S — Прямая угроза  
**Чем силён:** Единственный полноценный соперник: 418 тестов, p50 1368 мс, три поверхности API, hash-chain, judge-solo  
**Где пробивается:** Основной LLM — Groq, не LLM Gateway. Precision 1.00 на самоправленой выборке 70 реплик. Хеши без соли. 11 коммитов

**1. Что построено**

«ИИ-свидетель» для регулируемых продаж страховок и кредитов в Индии: ноутбук между агентом и клиентом слушает диалог на English/Hindi/Hinglish, диаризует двух говорящих, проверяет каждую финализированную реплику против «протокольного пакета» регулятора (8 обязательных раскрытий + 6 запрещённых утверждений, каждое с цитатой нормы), и при подтверждённом запрещённом утверждении **перебивает вслух** заскриптованной коррекцией под 20 слов. В конце задаёт 3–5 teach-back вопросов клиенту, слушает ответы на хинглише, выставляет вердикт по каждому и выдаёт хеш-цепочный сертификат, верифицируемый третьей стороной в браузере. Два пакета: `insurance-ulip-in` (IRDAI) и `loan-kfs-in` (RBI KFS).

**2. Как использован AssemblyAI**

Самое плотное и самое грамотное использование API среди разобранных — задействованы **три** поверхности одновременно:
- **Streaming STT**: `streaming.assemblyai.com/v3/ws`, модель `universal-3-5-pro`, PCM16 mono **24 kHz**, `speaker_labels`, `max_speakers=2`, `language_codes` (как JSON-array-строка, не повторяющиеся query-параметры — отдельно задокументировано), `format_turns=true`, keyterms из имён и продуктовых терминов комнаты.
- **Voice Agent API**: `agents.assemblyai.com/v1/ws`, `session.update` для мутабельных полей, каждая произносимая строка — скриптованный `reply.create` («verbatim in 10 of 10 trials»), сброс плейбека на `input.speech.started`, корректный `session.end` перед закрытием. Client-side tools с удержанием `tool.result` до момента, когда `reply.done` — последнее событие, плюс задокументированное hold-mode исключение для `finish_teachback`. Есть **progressive tool reveal**: `finish_teachback` появляется только после трёх записанных ответов, и промпт меняется тем же сообщением.
- **LLM Gateway** — как fallback-эндпоинт за OpenAI-совместимым провайдером; основной путь — Groq gpt-oss со strict JSON schema. Клиент умеет оба: bare key + `json-repair` для гейтвея, `Bearer` + `reasoning_effort` для Groq, три режима JSON в зависимости от того, что модель реально enforce-ит.

Раздел «What we learned about the AssemblyAI API» — фактически багрепорт на API, который судья-инженер AssemblyAI прочитает с интересом: `SpeakerRevision` переставил 5 из 8 устоявшихся реплик на другого спикера (включая два раскрытия) на синтетических голосах, поэтому теперь он дозаполняет только `PENDING`; `conversation.message` не читается следующим `reply.create`, а приложение к `system_prompt` — читается; при включённой диаризации `mode` игнорируется, реплики форс-финализируются на 10 с, партиалы замедляются до ~3 с без `continuous_partials=true`, а `format_turns` по умолчанию false, так что `turn_is_formatted` никогда не переключится; `Turn.language_code` — подсказка, а не гарантия (короткие английские реплики приходили с тегом `et`); две официальные страницы документации противоречат друг другу по таймингу `tool.result`.

**3. Архитектура и стек**

Next.js 15.5.25 / React 19.1 / TypeScript на Vercel, zustand для состояния, zod для схем, shadcn + @base-ui/react, Upstash Redis (KV) для сертификатов. Аудиопуть целиком в браузере: Mic AudioWorklet (PCM16 mono 24 kHz) → Audio Router/Mixer, куда подмешивается синтетический advisor в judge-solo → одновременно две сокет-ветки: бинарный PCM каждые 50 мс в STT («ears») и base64 PCM каждые 50 мс в Voice Agent («mouth»), причём вторая **гейтится по фазе** сессии. Session State Machine кормит детерминированный Rule Engine (протокольный пакет) и UI. Серверные route handlers: `/api/token/stt`, `/api/token/agent` (минтят одноразовые токены, валидные 60 с — ключ в браузер не попадает), `/api/analyze`, `/api/teachback/questions`, `/api/certificate`, страница `/verify/[id]`. Тесты: vitest + Playwright, включая live-e2e с fake mic через `SAAKSHI_FAKE_WAV`.

**4. Настоящая инженерная суть**

Нетривиального много, и оно не в обёртке:
- **Двухсокетная архитектура с раздельным гейтингом одного микрофонного потока.** Один PCM-источник кормит и распознаватель, и голосового агента, но в агента он идёт только в разрешённой фазе — иначе агент реагирует на всё подряд и перебивает сам себя. Микшер + флеш плейбека на `input.speech.started` — та работа, которую большинство участников не делает.
- **Разделение словарей keyterms.** Интеллектуальное ядро проекта: keyterms улучшают распознавание именно перечисленных слов, поэтому если скормить распознавателю фразы, которые ищут правила, ошибка распознавания «защёлкнется» на раскрытие, которого никто не делал. Решение: в распознаватель идут только identity-термы (имена, продукт, регулятор), а фразы раскрытий и запрещённых утверждений — нет. Есть юнит-тест, доказывающий, что ни один identity-терм не может сам закрыть правило, и live-прогон на идентичном аудио без потери recall.
- **Разделение полномочий LLM/правил.** LLM физически не может поставить галочку, поднять флаг или заговорить — только оставить советническую заметку ревьюеру. Это архитектурное, а не промптовое ограничение.
- **Hash-chain в двух местах.** Браузер строит цепочку по финализированным репликам, сервер **пересчитывает** цепочку и хеш сертификата перед записью и отказывает всему, что не верифицируется. Хранятся хеши слов, не слова; аудио не записывается вообще.
- **Judge-solo mode** — синтетический advisor проигрывается в тот же микрофонный поток, чтобы диаризация нашла двух говорящих, при этом он не отправляется в Voice Agent и ждёт тишины перед каждой репликой. Чистая забота о том, чтобы демо работало у судьи в одиночку.

Обёрткой над API здесь можно назвать разве что UI-слой.

**5. Метрики и доказательства**

Самая сильная доказательная база среди разобранных. Все числа заявлены как продукт живых прогонов против реальных API, у каждого указана команда:
- Время до перебивания, от конца речи до первого звука: **p50 1368 мс, max 1538 мс**, 10 интервенций, `pnpm test:e2e:latency`.
- LLM-слой на запрещённых утверждениях и раскрытиях: **precision 1.00, recall 1.00, 10 из 10 диалогов, p50 1.3 с** (`pnpm eval:analyzer`).
- Раскрытий поймано за один проход демо-скрипта: **7–8 из 8** (identity-only словарь).
- Раскрытий отмечено ложно (никогда не произносились): **0 из 12** — omitted-disclosures запись, три режима словаря.
- Стоимость одной демо-сессии: **~$0.16** по списочным ценам за billed seconds.
- Генерация teach-back вопросов: **1.7 с**, один раз за сессию, **5 из 5** сохранены.
- Judge-solo: перебивание на **2226 мс** (заметно хуже 1368 — указано честно).
- Rule engine против 70 размеченных реплик: **precision 1.00, recall 1.00**.
- **418 юнит-тестов** проходят.

Отдельно — редкая для хакатона интеллектуальная честность: корпусная оценка прямо названа «regression suite, not a generalisation estimate», с рассказом, что 70 реплик разметили вручную, движок разошёлся с разметкой на 18, 9 паттернов были реально неверны и исправлены, одна метка была слишком строгой и поправлена. И то же самое написано на публичной странице `/metrics`. Латентность репортится как «endpointing lag распознавателя + собственная реакция», и бейдж показывает «reply only», когда end-to-end посчитать нельзя.

**6. Сильные стороны**

- **Application of Technology**: три поверхности AssemblyAI, глубокие фичи (диаризация, `format_turns`, keyterms, client-side tools с корректным таймингом, progressive tool reveal) и раздел выученных уроков, читающийся как QA-отчёт по самому API. Выигрышный профиль именно в этой категории.
- **Presentation**: живое демо на Vercel, публичная страница метрик с командами, скриншоты hero/room/verify/metrics, mermaid-диаграмма архитектуры, judge-solo для демонстрации одним человеком, tampered-сертификат рядом с валидным.
- **Business Value**: конкретная боль с числом от регулятора — 26 667 жалоб на мис-селлинг к life insurers за FY25, +14%; TAM — 5.8 млн лицензированных продающих мест; продукт per-seat на уже стоящем на столе ноутбуке; новый регулятор = JSON-файл, а не код.
- **Originality**: «перебей продавца в моменте + выдай верифицируемый сертификат согласия» — не пост-анализ комплаенса, а интервенция в реальном времени. Хинглиш code-switching внутри одного предложения почти никто не делает.

**7. Слабые места и уязвимости**

- **11 коммитов** при объёме репозитория, выглядящем как несколько недель работы. Судья, смотрящий на историю, увидит либо squash, либо перенос кода — а clean-room заявления, как у voice-action-gate, здесь нет. Самая мягкая точка: «покажите историю разработки».
- `languages` пустое — отдача GitHub по языкам не заполнена, то есть репозиторий свежий или перезалит.
- **Перебивание вслух продуктово спорно.** Судья с опытом в продажах спросит: что происходит при ложном срабатывании в присутствии клиента? Ущерб от одного ложного перебивания больше, чем от пропущенного раскрытия. Заявлено 0/12 ложных тиков, но false-positive rate именно **перебиваний** (а не тиков) отдельно не измерен.
- **precision/recall = 1.00 на 10 диалогах и 70 репликах** — выборка, на которой 1.00 означает «не хватило данных, чтобы найти ошибку». Авторы это признают, но признание не создаёт генерализующей оценки.
- **Зависимость от внешнего Groq**, а AssemblyAI LLM Gateway — лишь fallback, потому что «единственная модель, до которой дотягивается этот аккаунт», ошиблась (пометила правдивое предложение как запрещённое утверждение через реплику после раскрытия lock-in). На хакатоне AssemblyAI это риторический минус: основной путь идёт не через инструмент организатора.
- **Приватность**: заявлено «аудио не записывается никогда» и «хранятся хеши, не слова» — но хеш реплики из известного протокольного пакета брутфорсится тривиально для коротких фраз. Если сертификат хранит хеши отдельных реплик без соли, содержание он не защищает. Соль в README не упомянута.
- Подозрительные зависимости: `cn@^0.2.5` и `shadcn@^4.21.0` в **dependencies** (shadcn — CLI, ему место в devDependencies), `lucide-react@^1.41.0` — нетипичный мажор. Мелочь, но цепляет глаз ревьюера.
- Fixtures рендерятся **PowerShell-скриптами** (`render-test-wav.ps1`, `render-latency-wav.ps1`, `render-customer-wav.ps1`, `render-omitted-wav.ps1`) — воспроизводимость на macOS/Linux у судьи ломается.

**8. Чем это можно побить**

Их слабое место — недоказанная генерализация и неизмеренная цена ложного перебивания. Ход: в той же категории «real-time compliance intervention» принести **измеренную ROC-кривую по порогу интервенции** на корпусе, который мы не размечали сами — публичный датасет диалогов или минимум 200 реплик, размеченных двумя независимыми аннотаторами с Cohen's kappa. Там, где Saakshi говорит «precision 1.00 на 70 регрессионных репликах, но это не оценка генерализации», мы говорим «precision 0.93 при recall 0.88 на held-out наборе, порог выбран так, что ложное перебивание стоит в 8 раз дороже пропуска, вот кривая». Инженерный судья ценит измеренный trade-off выше недостижимой 1.00.

Второй ход — **закрыть их приватностную дырку и сказать это вслух**: hash-chain с per-session HMAC-ключом и Merkle-деревом, публикация только корневого хеша, плюс selective disclosure (клиент раскрывает одну реплику и доказывает её вхождение, не раскрывая остальные). Это на порядок серьёзнее «хешей слов» и бьёт прямо в их тезис «consent you can prove».

Третий — **не перебивать вслух, а перебивать приватно** в наушник продавца, с эскалацией в вслух только на повторе. Снимает главное продуктовое возражение и звучит как решение человека, который разговаривал с реальными продавцами.
