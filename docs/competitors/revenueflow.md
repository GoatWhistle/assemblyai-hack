**1. Что построено**

Голосовой ресепшн для латиноамериканских малых бизнесов внутри WhatsApp: клиент присылает голосовую заметку, система транскрибирует её, извлекает интент, разрешает относительную дату («el jueves en la tarde») в реальный timestamp в таймзоне бизнеса, проверяет фактическую доступность в календаре и записывает на приём. Мультитенантный SaaS на Next.js + Supabase с двумя активными «country packs» — Венесуэла и Бразилия. Заявленное время цикла — «под десять секунд» в README и «около семи секунд» в описании на девпосте (уже несогласованность двух цифр в собственных материалах).

**2. Как использован AssemblyAI**

Это единственный проект разобранных проектов, который использует **два** продукта AssemblyAI под одним ключом и честно это описывает:

- **Speech-to-Text: Universal-3.5 Pro** — асинхронная транскрипция файла голосовой заметки (не стриминг; голосовая нота — это готовый аудиофайл, стриминг здесь не нужен, и его отсутствие не является слабостью).
- **LLM Gateway** — извлечение интента. Модель по умолчанию `qwen3.5-4b-32k-fast` через переменную `LLM_GATEWAY_MODEL`. Есть скрипт `scripts/probe-models.mts`, который проверяет, к каким моделям есть доступ у аккаунта — признак того, что автор реально воевал с Gateway, а не скопировал пример из документации. Отдельная деталь: модели, принимающие `response_format: json_schema`, используют его автоматически, остальные получают схему в промпте и валидируются Zod на возврате.
- Тонкая работа с языковой детекцией (из devpost-описания, в README не раскрыто): `expected_languages`, фолбэк по стране, `code_switching` для смешанных нот и `on_low_language_confidence: fallback` — «шумная нота деградирует до языка страны, а не падает». Это ровно тот набор флагов Universal, который знает человек, читавший документацию целиком.
- Язык транскрипции диктуется country pack: венесуэльский тенант — `es`, бразильский — `pt`.
- Зависимость `assemblyai@^4.37.0` в `package.json` — официальный SDK, не сырые HTTP-вызовы.
- Каждая секунда аудио пишется в `usage_events` — учёт потребления API на уровне продукта.

Чего **нет**: Voice Agent API, speaker labels, turn detection, tool calling на стороне AssemblyAI, TTS. Судья по критерию «Application of Technology» может сказать: это STT + LLM-прокси, а не голосовой агент в полном смысле. Ответы клиенту, по признанию автора, — «hand-written templates», то есть исходящей генерации речи нет вообще.

**3. Архитектура и стек**

Next.js 16.3.3 / React 19.2.8 / TypeScript, Tailwind 4, Zod 4 для валидации, Supabase (Postgres + RLS) как БД и auth, деплой на Vercel (`vercel.json`), миграции своим скриптом `scripts/migrate.mts` с таблицей `_migrations` (идемпотентность) и перезагрузкой кэша схемы PostgREST. Vitest для тестов, Playwright в devDependencies.

Поток аудио имеет **два входа, сходящихся в одну функцию** `ingestVoiceNote()` в `src/lib/ingest/voice-note.ts`:
- `POST /api/voice` — рекордер в браузере, для демо, «nunca depende de Meta» (никогда не зависит от Meta);
- `POST /api/webhooks/whatsapp` — прод, с проверкой HMAC-SHA256 по сырому телу.

Дальше: `audio → транскрипция → интент → реальная доступность → назначенная встреча` (`src/lib/agent/`), планировщик в `src/lib/agent/scheduling.ts`. Country packs изолированы в `src/lib/country/`, схема и RLS в `supabase/migrations/`, есть fallback-путь через `supabase/APLICAR-TODO.sql` для ручного применения. В README отдельно разобран диагноз блокировки порта 5432 в residential-сетях с переходом на 6543 и скриптом `scripts/probe-db.mts` — это следы реальной эксплуатации, а не написанного «для галочки» руководства.

**4. Настоящая инженерная суть**

Тут реально есть что защищать, и это не про AI:

- **Архитектурный инвариант «модель решает что, система решает что можно»**, доведённый до кода: модель выбирает только id из каталога тенанта; возвращает не дату, а день недели + слот, реальную дату считает система в таймзоне бизнеса; слот берётся из `availability_rules` минус занятые записи, а **уникальный индекс в Postgres физически запрещает двойную бронь**. Это правильный ответ на «LLM галлюцинирует» — не промпт-инжиниринг, а constraint на уровне БД.
- **Graceful degradation вместо ошибки**: если ответ модели не проходит схему, система не бросает 500, а возвращает интент «эскалировать человеку». Формулировка автора точная: «клиент, ждущий в WhatsApp, заслуживает, чтобы им кто-то занялся, а не 500».
- **Идемпотентность по `external_id`** — WhatsApp ретраит вебхуки, без этого одно аудио транскрибируется и биллится дважды. Это знание из эксплуатации, не из туториала.
- **Сообщение сохраняется до транскрипции**; при отказе провайдера аудио остаётся в состоянии `FAILED` с текстом ошибки, то есть данные клиента не теряются.
- **Деньги как составной тип**, а не число: сумма хранится с валютой, курсом, источником курса, датой и замороженным USD-эквивалентом. Тест 7 отвергает сумму двойной валюты без курса. Для Венесуэлы это не педантизм, а единственный способ, чтобы данные через три дня что-то значили.
- **Архитектурный тест как fitness function**: тест 8 проверяет, что вне `src/lib/country/` нет ни одного литерала страны. Добавление Колумбии = написать pack, не трогая движок. Такие тесты в хакатонных проектах не встречаются практически никогда.
- **Тесты RLS вместо тестов «оно запустилось»**: 1) пользователь видит только лиды своего тенанта; 2) запрос чужого лида по id возвращает 0 строк; 3) вставка с чужим `tenant_id` отвергается; 4) регистрация атомарна, без сирот-тенантов; 5) ни одна таблица не осталась без RLS. Плюс валидаторы контрольных цифр CPF/CNPJ/RIF/cédula.
- **Удержание контекста диалога**: четыре слова «mejor para el viernes» переносят нужную запись на пятницу на тот же час без повторения услуги и даты (из devpost). Это не тривиально — это coreference над состоянием записи.

Обёртка над API — только сам вызов транскрипции. Всё остальное — предметная инженерия, и это ровно то, чего у остальных четырёх нет.

**5. Метрики и доказательства**

- Тестов: **8 сценариев в README** — и это важная деталь. В devpost-описании автор заявляет **177 тестов**. README перечисляет 8 пунктов таблицы (вероятно, 8 групп, 177 кейсов), но из репозитория это не выводится. Расхождение 8 vs 177 — готовая точка укола.
- Тесты 1–5 требуют Supabase и **помечаются как `skip` без креденшелов, а не дают ложный зелёный** — это интеллектуальная честность, которую стоит отметить, но она же означает, что в CI без секретов реально проверяются только 3 теста из 8.
- Латентность: «under ten seconds» (README) / «about seven seconds» (devpost). **Замеров нет.** Ни таблицы p50/p95, ни разбивки по этапам (скачивание медиа из WhatsApp / транскрипция / LLM / запись в БД). Для проекта, где скорость — часть питча, это дыра.
- Точность транскрипции, WER на венесуэльском/бразильском аудио — **не измерено вообще**, несмотря на всю тонкую настройку `expected_languages` и `code_switching`.
- Есть `npm run doctor` — проверка креденшелов, миграций и демо-данных без печати секретов. Хорошая инженерная гигиена, не метрика.
- Есть e2e-скрипт: `node --conditions=react-server --import tsx scripts/try-agent.mts audio.wav VE` — прогон всего конвейера на файле. Условие `react-server` нужно из-за `server-only` в пайплайне; такую деталь не придумывают.
- 51 коммит — второй показатель среди разобранных, свидетельство реальной итеративной работы.

**6. Сильные стороны**

- **Business Value — сильнейший среди разобранных.** Ниша конкретна, не гипотетична: WhatsApp в LatAm как основной канал, голосовая заметка как норма общения, а любая CRM рисует серый квадрат «audio message». Автор попал в реальный workflow, который никто не автоматизировал.
- **Originality**: не «ещё один медицинский скрайб» и не «ещё один финансовый ассистент» — категория, где он один. Полноценные locale-паки (es/pt, CPF/CNPJ/RIF, LGPD) показывают, что рынок понят изнутри.
- Публичное демо с тестовым логином — судья заходит и щёлкает за 30 секунд, микрофон не нужен.
- Раздел «Pendiente antes de producción» с четырьмя незакрытыми пунктами, включая признание, что алгоритм контрольной цифры RIF не сверен с реестром SENIAT. Такая открытость обезоруживает половину вопросов судьи.
- Единственный провайдер: STT и LLM — один ключ AssemblyAI. Для спонсорского хакатона это ровно тот нарратив, который спонсор хочет слышать.
- Заявлено, что работает на реальном WhatsApp-номере в двух странах, с row-level изоляцией тенантов и MIT-лицензией.

**7. Слабые места и уязвимости**

- **Это не voice agent.** Хакатон называется Voice Agent Hackathon. Здесь нет диалога, нет TTS, нет turn detection, нет barge-in, нет tool calling внутри Voice Agent API. Односторонний конвейер «аудио → действие» с текстовыми шаблонами на выходе. Судья по «Application of Technology» может резать здесь глубоко: использованы два продукта, но не тот флагманский, ради которого хакатон.
- **Ответы — захардкоженные шаблоны.** Автор подаёт это как фичу (точные даты нельзя галлюцинировать), и защита валидна, но означает, что «понимание» ограничено извлечением интента: на любой вопрос за рамками сетки клиент получает шаблон или эскалацию.
- **Расхождение цифр**: 8 тестов vs 177; 7 секунд vs 10 секунд. Два материала одного автора противоречат друг другу.
- **Нулевая инструментация производительности.** Ни одного измеренного числа. Заявление «under ten seconds» непроверяемо и опирается на честное слово.
- **`middleware.ts` для обновления сессии не реализован** (в TODO) — сессии в проде истекают некрасиво.
- **Подтверждение email обходится** (`email_confirm` в seed) — для демо ок, для «работает на реальном WhatsApp-номере» это регистрация без верификации.
- **LGPD-политика хранения данных отсутствует**, а Бразилия объявлена активной страной. Медицинский тенант (Clínica Dental Sonrisa) + отсутствие retention policy = регуляторный риск, который автор сам признал, но не закрыл.
- **Presentation** — самое слабое место относительно остальных: README двуязычный, местами наполовину на испанском, с двумя подряд `---` (артефакт правки), **без единого скриншота, без видео, без диаграммы потока**. Veritas и VoiceMed уничтожают его на слайдах.
- Зависимость от Meta/WhatsApp Business API в проде не показана работающей: демо-путь сознательно обходит Meta («nunca depende de Meta»), то есть проверить прод-путь судья не может.
- `service_role` ключ Supabase проходит сквозь RLS — автор это честно помечает, но одна утечка в клиентский бандл Next.js сносит всю мультитенантную изоляцию.

**8. Чем это можно побить**

Их защита строится на «модель не может галлюцинировать, потому что мы ей не даём» — и достигается это отказом от генерации на выходе. Ход: **сделать полноценный двусторонний голосовой диалог на Voice Agent API, сохранив их же инвариант, но без шаблонов.** Конкретно:

1. **Взять их правило и усилить его до tool calling внутри Voice Agent API.** Они срезали генерацию, чтобы не галлюцинировать даты. Правильное решение — не убирать генерацию, а **сделать календарь инструментом**: `check_availability` и `book_slot` как client-side tools, где даты и слоты приходят из БД в аргументах результата, а модель их только озвучивает. Тот же класс гарантий (модель не изобретает слот), но на выходе живая речь, а не шаблон. Это прямо забирает у них аргумент «шаблоны — это фича».
2. **Заменить их непроверяемые «7–10 секунд» на измеренную таблицу.** Публикуем p50/p95 по этапам: время до первого слова транскрипта, до tool-результата, до первого аудио-ответа. Даже скромное «p95 = 1.4 с до первого аудио» рядом с их «около десяти секунд» выглядит как другой класс продукта, потому что это стриминговый диалог против батч-конвейера.
3. **Скопировать их лучший приём и добавить то, чего у них нет.** Их архитектурный тест «в ядре нет литералов страны» — умный ход; аналог у нас: fitness-тест «ни один пользовательский факт (дата, цена, слот, идентификатор) не попадает в ответ, минуя tool-результат». Плюс WER-замер на реальном шумном аудио целевого языка — метрика, которой нет ни у одного из разобранных проектов.
4. **Presentation, где они беззащитны.** У них ноль скриншотов и полуиспанский README. 90-секундное видео, где слышно живой диалог с barge-in, и один нарисованный поток аудио — и по критерию Presentation вопрос закрыт, при том что Business Value у них останется сильным.
