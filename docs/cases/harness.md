# Альтернатива: Harness — голосовой агент, который стресс-тестирует другие голосовые агенты

Кейс-документ по второй идее. Сравнивается с базовым вариантом [12-project-case.md](../cases/rxgate.md) (RxGate). Опирается на [10-assemblyai-signals.md](../assemblyai-signals.md) (рамка оценки от AssemblyAI), [08-assemblyai-tech-reference.md](../reference/assemblyai-api.md) (протокол, лимиты, ловушки), [06-assemblyai-feature-usage.md](../assemblyai-feature-usage.md) (что поле не использует), [09-strategy.md](../strategy.md) (расстановка сил), [04-competitor-teardown.md](../competitors.md) (разбор Voxrede).

Рабочее название — **Harness**. Слово несёт нужный смысл: это стенд, к которому пристёгивают тестируемое устройство, а не оружие против него.

Критическая самооценка — в разделе 13. Прочитать её стоит раньше остального, если решение принимается быстро.

---

## 1. Одно предложение

Голосовой агент, который сам звонит другому голосовому агенту, проговаривает с ним враждебный сценарий — шум, телефонные 8 kHz, быстрая и акцентированная речь, перебивания посреди фразы, code-switched реплики, реплики с высокой плотностью сущностей — и выдаёт измеренный отчёт: Entity Error Rate, P50/P95/P99 латентности по компонентам, barge-in rate, caller repeat rate, task completion rate и коды закрытия WebSocket, каждое число с воспроизводимой методикой.

## 2. Проблема

AssemblyAI 8–9 сентября 2026 опубликовала три статьи ([сигналы AssemblyAI](../assemblyai-signals.md)), которые вместе описывают одно: голосовые агенты выходят в прод без измерений, и ломаются они не там, где люди смотрят.

**Тезис, вокруг которого строится всё.** Дословно из их статьи:

> Голосовой агент — это цепочка, и LLM никак не может узнать, что его вход был неверным.

То есть у разработчика нет сигнала ошибки. Агент не падает — он уверенно делает не то.

**Числа, задающие масштаб** (все из [сигналы AssemblyAI](../assemblyai-signals.md), источник — AssemblyAI):

| Факт | Значение |
|---|---|
| Entity Error Rate у Universal-3.5 Pro Realtime | **15,31%** при WER **6,99%** |
| Entity Error Rate у Deepgram Flux | 50,50% при WER 15,58% |
| Ошибки на именах собственных / местах / телефонах | 16,92% / 6,28% / 3,55% |
| Успех пятиходового сценария при точности захвата 84,69% за ход | **43,6%** |
| Тот же сценарий с шагами подтверждения | **79,1%** (подтверждение ловит 70% ошибок) |

Первые две строки — почему WER не работает как метрика приёмки: модель, пропускающая половину именованных сущностей, всё ещё показывает WER, который выглядит защитимо. Третья и четвёртая — почему одноходовое тестирование обманывает: 84,69% за ход выглядят нормально и превращаются в 43,6% за пять ходов.

**Пороги, которые AssemblyAI объявила целевыми:**

| Метрика | Порог |
|---|---|
| finalization delay, P95 | < 500 мс |
| LLM time-to-first-token | низкие сотни мс |
| TTS time-to-first-byte | < 300 мс |
| end-to-end | < 1 с |
| P95 time-to-first-audio (порог алерта) | > 1500 мс в течение 5 минут — алерт |
| caller repeat rate | +2 пункта неделя к неделе — алерт |
| barge-in rate | +5 пунктов неделя к неделе — алерт |

**Что ломается первым**, в их порядке: установка соединения при всплеске, очередь на LLM, backpressure у TTS, round-trip вызовов инструментов. И отдельно: **точность STT при нагрузке стабильна, деградацию даёт реальное аудио** — 8 kHz телефония, шум, перебивания. Это прямое указание, что стресс-тест голосового агента — это не «1000 параллельных сессий», а «50 худших звонков».

**Операционные обрывы, которые надо логировать:**

| Код закрытия | Значение |
|---|---|
| 3007 | Некорректные аудио-чанки (вне диапазона 50–1000 мс) |
| 3008 | Достигнут трёхчасовой лимит — утечка биллинга |
| 3009 | Превышен лимит сессий |

И лимиты, в которые тестировщик упирается первым: **5 новых сессий в минуту на free tier, 100+ на paid**, автоскейл на 10% при утилизации выше 70%, жёсткого потолка конкурентности нет; биллинг по длительности WebSocket, **не** по объёму аудио, **idle тарифицируется**; автозакрытие сессии через 3 часа. Их собственное предупреждение: тест из тысячи звонков без аккуратной очистки выставит счёт за 8+ часов, которых не было — незакрытые сессии держатся 30 секунд (Voice Agent API) или 3 часа (streaming).

**И главный факт про поле.** Сопоставление того, что AssemblyAI объявила признаком зрелости, с тем, что сделали 45 сабмишенов ([использование фич](../assemblyai-feature-usage.md), [сигналы AssemblyAI](../assemblyai-signals.md)):

| Признак зрелости по версии AssemblyAI | Сколько из 45 сделали |
|---|---|
| Entity Error Rate как метрика | **0** |
| Caller repeat rate | **0** |
| P50/P95/P99 латентности по компонентам | **0** (есть заявления «под 300 мс» без методики) |
| Логирование close codes 3007/3008/3009 | **0** |
| Нагрузочное тестирование с профилями | **0** |
| Измеренная латентность вообще | 1 (Saakshi, p50 1368 мс) |

Продукт, который берёт эти три статьи и превращает их в работающий инструмент, попадает в критерий «Application of Technology» в том виде, в каком его понимают именно эти судьи — Dylan Fox (CEO), Luka Chkhetiani (Head of Realtime), Dan Ince (PM), Craig Bruder (Forward Deployed Engineer), Harnoor Singh (DevRel).

## 3. Почему именно эта ниша — и честно про Voxrede

В нише «тестирование голосовых агентов» из 45 сабмишенов **один** проект: **Voxrede** (himanshu748), разбор в [04-competitor-teardown.md](../competitors.md). Он серьёзный, и делать вид, что его нет, нельзя.

**Что у Voxrede реально хорошо:**

- Две сессии Voice Agent API, сбриджованные сервер-сайд audio-to-audio, без браузера и медиа-сервера. Это применение, до которого сам AssemblyAI, вероятно, не додумался.
- **Пейсер-инсайт** — лучший вклад проекта и то, что судья-инженер процитирует: каждая сторона гоняет real-time pacer, отдающий один PCM16-кадр 50 мс каждые 50 мс, несущий речь собеседника, когда она есть, и тишину, когда её нет. Дословно: *«turn detection measures silence in the stream, so a gap in the stream is not the same thing as silence in it. Without the pacer the two agents talk over each other and never yield a turn.»*
- Детерминированный скорер при стохастическом стимуле: один лог всегда скорится одинаково, произнесённые цифры нормализуются («four four seven one» матчится с `4471`).
- Научная гигиена: `PASS` объявлен как «no configured rule matched the recorded sample; this does not certify safety», есть отдельный вердикт `INCONCLUSIVE`, свой же fix-rate дисквалифицирован («This is not a measured fix rate»), невоспроизведшаяся атака показана честно.
- 29 коммитов, CI-бейдж, четыре тест-файла, каждая находка трассируется к событию с таймкодом.

**Где он пробивается — и это не придирки, а структурные дыры:**

| Слабость Voxrede | Почему это фатально |
|---|---|
| **Тестирует агентов, которых сам написал.** README признаёт: «The target agents are fixtures written for this project» | Демонстрирована уязвимость собственной фикстуры, а не голосовых агентов как класса. Без хотя бы одного прогона против внешнего агента доказательная сила близка к нулю |
| **Демо не подключается ни к чему живому**: «It does not connect to an existing deployed agent or dial a phone number» | Как продукт пути к клиенту нет: ни телефонии, ни интеграции с развёрнутым агентом. Их же фраза: «reproducing a prompt is not equivalent to testing its production integration» |
| **n=1 и n=2 везде.** 2 из 6 атак сломали цель; 5 находок → 0 по двум сэмплам; повторяемость проверена на двух атаках, и **одна из двух не воспроизвелась** | Они сами пишут, что находка — доказательство достижимости, а не оценка частоты, и что повторные прогоны отличают стабильную слабость от везения. И сами этого не делают |
| **Публичное демо — статические архивные страницы.** Guided review не требует ключа именно потому, что это отрендеренный архив | Судья, который хочет нажать кнопку и увидеть прогон, не может |
| **Минимальная глубина AssemblyAI на уровне STT.** Ни модель не названа, ни `speaker_labels`, ни `format_turns`, ни keyterms, ни `words[]` | Voice Agent API инкапсулирует распознаватель — значит работы с распознавателем в проекте нет. По «Application of Technology» это поверхностно |
| **Этическая мина**: инструмент, автоматически ломающий голосовых агентов, публичен под MIT. «Point this only at agents you own» — оговорка, а не механизм | Судья от AssemblyAI может насторожиться: инструмент атакует агентов, построенных на API организатора |
| Восемь markdown-файлов в корне и пять генераторов статических страниц | Соотношение презентационного кода к продуктовому настораживает |

**Чем Harness отличается принципиально, а не косметически.**

Не «то же, но лучше». Другая ось:

1. **Voxrede мерит безопасность. Harness мерит качество и латентность.** У Voxrede вердикт бинарный: политика нарушена или нет, находка есть или нет. Ни латентности, ни точности распознавания — и для их продукта это правильно. Harness мерит непрерывные величины по рамке, которую опубликовала AssemblyAI: EER, процентили латентности, repeat rate, barge-in rate, task completion. Это не конкурирующие продукты, это соседние. И вторая ось — ровно та, которую объявил важной организатор.

2. **Harness превращает n=2 в частоту.** Voxrede сам призывает к повторным прогонам и не делает их. Harness делает breach/degradation rate с **интервалом Уилсона** на N≥20 прогонов на сценарий и разделяет сценарии на стабильные и флейки. Это буквально исполнение их же рекомендации.

3. **Harness обязан прогоняться против не-своего агента.** Минимальный честный вариант, который не требует чужого согласия: **агент, собранный по официальному quickstart AssemblyAI без изменений** — «то, что построит средний разработчик по документации». Промпт писали не мы. Заголовок «мы прогнали агента из официального quickstart на 200 звонков и вот его P95 и EER» бьёт «мы сломали свою фикстуру» насмерть.

4. **Живая кнопка вместо архива.** Одной кнопки «запустить прогон сейчас» с потоковым выводом событий достаточно, чтобы забрать Presentation в этой нише.

5. **Глубина на уровне распознавателя.** Voxrede не трогает Streaming STT. Harness без него не работает: EER считается по `words[]` с `confidence`, finalization delay — из сообщений `Turn`, repeat rate — по финальным транскриптам. Это ровно те редкие фичи, которые по [использование фич](../assemblyai-feature-usage.md) заняты 2–3 проектами из 45.

6. **Этика встроена как механизм, а не оговорка.** Подробно в разделе 7: allowlist целей, обязательный токен владения, отсутствие телефонии в публичной сборке, rate limit на прогоны.

**Риск позиционирования, который надо назвать сразу.** Ниша занята не только Voxrede. Voxrede сам честно пишет про Bluejay («lists red teaming alongside its simulation product, and integrates with the same Voice Agent API»), и за ним стоит целая категория voice-agent-eval стартапов — Coval, Hamming, Vocera и другие. Это означает, что **Originality здесь ниже, чем у RxGate**, и притворяться иначе нельзя. См. раздел 13.

## 4. Что именно происходит в продукте

### Основной поток

Оператор (QA-инженер команды, которая эксплуатирует голосового агента) делает три вещи:

1. Регистрирует цель: WebSocket-эндпоинт своего агента + токен владения. Либо выбирает одну из встроенных референсных целей.
2. Выбирает **профиль нагрузки** — набор сценариев и число прогонов на сценарий.
3. Нажимает «Прогнать» и смотрит, как заполняется отчёт.

### Сценарии (attack/degradation profiles)

Сценарий — это данные, не код: JSON с инструкцией для агента-звонящего, ожидаемой структурой задачи, набором аудио-деградаций и правилами скоринга. Семь классов, каждый выведен из конкретного утверждения AssemblyAI:

| Класс | Что делает | Откуда взялось |
|---|---|---|
| `entity_dense` | Диктует последовательность сущностей: номер заказа, дата, имя, адрес, телефон | EER 15,31%; имена собственные 16,92%, места 6,28% |
| `five_turn_chain` | Пятиходовое бронирование с сущностью на каждом ходу, успех = все пять сущностей дошли верными | Их 84,69% за ход → 43,6% за пять ходов |
| `telephony_8k` | То же аудио, но 8 kHz μ-law (`pcm_mulaw` / `audio/pcmu`) вместо студийного | «деградацию даёт реальное аудио, а не модель» |
| `noise_and_accent` | Подмешанный фоновый шум, ускоренный темп, акцентированная речь | их корпус «50 худших звонков» |
| `barge_in` | Звонящий перебивает цель посреди её реплики, и наоборот | barge-in rate как метрика разговора |
| `code_switch` | Реплика с переключением языка посреди фразы (en↔es, en↔hi) | −22% относительного WER на code-switched, 18 языков в streaming |
| `repeat_pressure` | Звонящий повторяет ту же фразу, если цель не поняла — до трёх раз | caller repeat rate: 19% на email против 1% на да/нет |

Ключевая деталь: `telephony_8k` — это **тот же текст, то же ground truth, другой канал**. Значит дельта EER между `entity_dense` и `telephony_8k` — чистый эффект канала, а не разных данных. Это единственный способ получить осмысленное число, и он же — прямая проверка их утверждения про реальное аудио.

### Что видит оператор во время прогона

Живая трёхколоночная раскладка:

- **Слева** — таймлайн событий обеих сторон на одной шкале: `input.speech.started`, `transcript.user`, `reply.started`, `reply.audio` (первый байт), `reply.done` (`completed` / `interrupted`), `tool.call`, `session.error`, close code. Каждое событие с монотонным таймстемпом.
- **Центр** — два транскрипта друг против друга: что сказал звонящий (ground truth известен по построению) и что цель услышала. Расхождения по сущностям подсвечены.
- **Справа** — счётчики, растущие в реальном времени: прогон 7 из 20, текущий P95, EER на завершённых прогонах, число обрывов.

Цель: `quickstart-reference-agent` (агент, собранный по официальному quickstart AssemblyAI без изменений). Профиль: `full`, N = 20 прогонов на сценарий, 140 звонков.

Разбивка латентности по компонентам, тот же прогон (всё **иллюстративно**):

| Компонент | P50 | P95 | P99 | Порог AssemblyAI | Вердикт |
|---|---|---|---|---|---|
| finalization delay (конец речи → финальный `Turn`) | 310 мс *(илл.)* | 470 мс *(илл.)* | 610 мс *(илл.)* | < 500 мс P95 | в норме |

Repeat rate с сегментацией по предшествующему вопросу цели — тот разрез, который AssemblyAI называет способом найти горячие точки (их пример: 19% на запросе email против 1% на да/нет). **Иллюстративно:**

| Вопрос цели | Repeat rate |
|---|---|
| «какой номер заказа» | 24% *(илл.)* |
| «продиктуйте адрес» | 19% *(илл.)* |
| «ваш email» | 31% *(илл.)* |
| «подтверждаете?» (да/нет) | 2% *(илл.)* |

Строка `five_turn_chain` против `five_turn_chain + confirmation` — ключевая. Это A/B, воспроизводящий их 43,6% → 79,1% **на чужом агенте, а не на своих данных**. Обратите внимание на цену: в иллюстративных числах подтверждение поднимает completion и **поднимает P95** — это и есть честный трейдофф, который отчёт должен показывать, а не скрывать.

И операционная секция, которую не сделал никто из 45:

| Событие | Число |
|---|---|
| close 3007 (битые чанки) | 0 |
| close 3008 (3-часовой лимит — утечка биллинга) | 0 |
| close 3009 (лимит сессий) | 3 *(илл.)* — на профиле `burst`, при 8 новых сессиях в минуту на free tier |
| `session.error` (Error frame залогирован целиком) | 2 *(илл.)* |
| суммарное billable WebSocket-время | 4 ч 51 мин *(илл.)* |
| из него idle | 18 мин *(илл.)* |

Строка 3009 — не баг, а **демонстрация того, что инструмент нашёл реальный лимит**: 5 новых сессий в минуту на free tier, и профиль `burst` в него упирается предсказуемо. Строка «из него idle» — прямое исполнение их предупреждения про счёт за часы, которых не было.

### Каждое число — с методикой

Под каждой таблицей в UI — раскрывающийся блок с: N, определением метрики, командой CLI, которой она получена, и ссылкой на сырой лог прогона. Ни одной цифры без методики — прямой контраст с полем, где у Veritas бенчмарки взаимно противоречивы, а у RevenueFlow 8 тестов в README против 177 на девпосте ([стратегия](../strategy.md)).

## 5. Архитектура

Стек: **FastAPI (Python) + React/TypeScript**.

### Главный вопрос: это вообще голосовой агент?

Это самое опасное место идеи, и решать его надо архитектурно, а не формулировкой в README.

**Постановка проблемы.** Инструмент, который только измеряет, — это тестовый харнесс. Ему по сути достаточно Streaming STT: записать аудио цели, распознать, посчитать. Voice Agent API в такой конструкции не нужен вообще. И тогда судья справедливо говорит: хакатон называется Voice Agent Hackathon, а вы принесли профайлер. По «Application of Technology» это может сработать (стек задействован глубоко), но по существу — вы не построили голосового агента.

**Решение: звонящий — сам полноценный голосовой агент.** Не проигрыватель WAV-файлов, а **сессия Voice Agent API**, которая ведёт разговор с целью: слушает её реплики через собственный STT, решает через LLM, что говорить дальше, говорит через TTS, перебивает по решению, вызывает инструменты. Именно это делает Voxrede, и именно поэтому его применение API судьи назвали самым необычным в батче.

Разница с Voxrede — в том, что звонящий у Harness **не только говорит, но и наблюдает через второй сокет**:

```
                  ┌──────── Harness caller ────────┐
                  │                                │
   Voice Agent API │ ведёт разговор:                │
   session A       │ система-промпт сценария,       │
                   │ tool calling, барж-ин по плану │
                  └───────────┬────────────────────┘
                              │ reply.audio (PCM16)
                              │
                     ┌────────▼────────┐
                     │  pacer 50 мс    │  один кадр каждые 50 мс:
                     │  + degrader     │  речь или тишина
                     │  (8k μ-law,     │
                     │   шум, темп)    │
                     └────┬───────┬────┘
                          │       │
              input.audio │       │ tap (тот же PCM)
                          ▼       ▼
                ┌──────────────┐  ┌─────────────────────┐
                │   ЦЕЛЬ       │  │  Streaming STT v3   │
                │ (агент под   │  │  session B          │
                │  тестом)     │  │  words[] start/end  │
                └──────┬───────┘  │  confidence         │
                       │          │  speaker_labels     │
                       │ ответ    └──────────┬──────────┘
                       │                     │
                       └──────► pacer ───────┤ tap
                                              │
                                    ┌─────────▼─────────┐
                                    │ Streaming STT v3  │
                                    │ session C         │
                                    │ (аудио цели)      │
                                    └───────────────────┘
```

Итого **три сокета на один звонок**: A — Voice Agent API для звонящего (разговорный контур), B и C — Streaming STT как независимые «микрофоны» на обеих сторонах, дающие `words[]`, таймкоды, `confidence` и диаризацию. Метрики считаются из B и C, потому что Voice Agent API их инкапсулирует и слов с уверенностью не отдаёт.

**Почему этот ответ судью устраивает:**

1. Звонящий проходит любой разумный тест на «голосовой агент»: слушает, думает, говорит, перебивает, вызывает инструменты, держит turn-taking. Это Voice Agent API целиком, а не half-duplex проигрыватель.
2. Наблюдатель требует Streaming STT с `words[]`, `confidence` и `speaker_labels` — фичи, занятые 2–3 проектами из 45 ([использование фич](../assemblyai-feature-usage.md)).
3. Гибрид «Voice Agent API + Streaming STT» — это ровно та архитектура, которую AssemblyAI объявила правильной: «каскадный пайплайн отлаживается, а чёрный ящик audio-in/audio-out не даёт увидеть ошибку распознавания» ([сигналы AssemblyAI](../assemblyai-signals.md)). 25 из 45 взяли только чёрный ящик.
4. Плюс дополнительная поверхность: сравнение **что звонящий сказал** (ground truth по построению) против **что независимый STT услышал** против **что цель, судя по её поведению, поняла**. Три точки вместо двух — это и есть инструментальная ценность.

**Честная оговорка, которую надо произнести самим.** Harness — это агент, чей разговорный партнёр не человек. Судья может считать это натяжкой. Ответ: Voxrede уже сдал именно такую конструкцию, и в разборе она названа сильнейшей стороной проекта, а не слабостью. Но риск остаётся, и он назван в разделе 11.

### Три сокета, три разных протокола — и три ловушки

Из [API AssemblyAI](../reference/assemblyai-api.md). На этом легко потерять несколько часов:

| | Voice Agent API (A) | Streaming STT (B, C) |
|---|---|---|
| Эндпоинт | `wss://agents.assemblyai.com/v1/ws` | `wss://streaming.assemblyai.com/v3/ws` |
| Авторизация | `Authorization: Bearer <key>` | `Authorization: <key>` — **без Bearer** |
| Аудио | base64 в JSON `{"type":"input.audio","audio":...}` | **бинарные** WebSocket-фреймы |
| Sample rate | PCM16 **24 kHz** (`audio/pcm`) или 8 kHz (`audio/pcmu`/`audio/pcma`) | по умолчанию **16 kHz** `pcm_s16le`; диапазон 8000–96000 |
| Чанк | ~50 мс рекомендуется, сервер буферизует | **50–1000 мс жёстко**, иначе close **3007** |
| Завершение | `{"type":"session.end"}` | `{"type":"Terminate"}` |
| Утечка при незакрытии | 30 секунд | **до 3 часов billable** |

Третья ловушка — та, которую AssemblyAI не пишет, а Voxrede нашёл: **пейсер**. Turn detection измеряет тишину **в** потоке, а разрыв потока тишиной не является. Если просто не отправлять кадры, пока звонящий молчит, цель не отдаст ход. Нужен непрерывный поток кадров по 50 мс, несущих либо речь, либо сгенерированную тишину. Мы этот инсайт цитируем с атрибуцией Voxrede — это дешевле и честнее, чем переоткрывать, и судья это оценит.

### Деградатор — место, где живёт собственная инженерия

Между pacer и целью стоит цепочка обработки. Именно она превращает «проигрывание файла» в стресс-тест:

| Деградация | Реализация | Обоснование |
|---|---|---|
| Телефонный канал | ресемпл 24k → 8k, кодирование в G.711 μ-law, обратно; отправка как `audio/pcmu` | AssemblyAI: «8 kHz mulaw телефония, не студийное аудио» |
| Фоновый шум | подмешивание на заданном SNR | их корпус 50 худших звонков |
| Темп | time-stretch без изменения тона | быстрая речь в их списке деградаций |
| Перебивание | подача речи звонящего в момент, когда от цели идёт `reply.audio` | barge-in rate как метрика |
| Дропы и джиттер | выбрасывание и задержка кадров | «что ломается первым: установка соединения, очередь LLM, backpressure TTS» |
| Чанки вне диапазона | намеренная отправка 20 мс или 2000 мс | воспроизведение close code **3007** — проверка, что цель это обрабатывает |

Последняя строка — отдельно ценная: это единственный способ проверить, что тестируемый агент вообще умеет обрабатывать обрыв 3007, а не падает молча. Ни один из 45 проектов close codes не логирует, значит ни один и не обрабатывает.

### Схема бэкенда

```

                  │  /targets   реестр целей + токены владения  │
                  │  /run       живой прогон: таймлайн, счётчики│
                  │  /report/N  отчёт: таблицы + методики       │
                  │  /compare   base vs hardened, Уилсон        │
                  └───────────────────┬────────────────────────┘
                            ws /ws/run│  (события прогона потоком)
                  ┌───────────────────▼────────────────────────┐
                  │                 FastAPI                     │
                  │                                             │
                  ├─ POST /api/targets          регистрация цели + токен владения
                  ├─ POST /api/runs             запуск прогона (профиль, N)
                  ├─ GET  /api/runs/{id}        статус, метрики, сырой лог
                  ├─ GET  /api/reports/{id}     собранный отчёт
                  │
                  ├─ caller.py        Voice Agent API session A, tool queue
                  ├─ pacer.py         50 мс кадры, монотонные часы
                  ├─ degrade.py       8k μ-law, шум, темп, дропы, bad chunks
                  ├─ observer.py      Streaming STT B и C, words[]/confidence
                  ├─ scorer.py        детерминированный: EER, completion, repeat
                  ├─ latency.py       P50/P95/P99 по компонентам

                  └─ ledger.py        billable-время, idle, close codes
                  │
                  └─ SQLite: цели, прогоны, события, аудио-пути, метрики
```

### Звонящий как агент: конфигурация

```json
{
  "type": "session.update",
  "session": {
    "system_prompt": "<сценарий: роль звонящего, задача, сущности, когда перебивать>",
    "greeting": "<первая реплика по сценарию>",
    "input": {
      "format": { "encoding": "audio/pcm" },
      "keyterms": ["<только identity-термы цели: название компании, имена>"],
      "turn_detection": {
        "vad_threshold": 0.5,
        "min_silence": 500,
        "max_silence": 2000,
        "interrupt_response": true
      }
    },
    "output": { "voice": "james", "format": { "encoding": "audio/pcm" } },
    "tools": [ /* см. ниже */ ]
  }
}
```

Инструменты звонящего — то, что делает его агентом, а не плеером:

| Инструмент | Что делает | `execution_mode` |
|---|---|---|
| `next_entity` | выдаёт следующую сущность сценария (номер, дату, адрес) — так ground truth генерируется звонящим, а не зашит в WAV | `interactive` |
| `mark_task_state` | звонящий сам фиксирует, дошла ли задача до конца — сигнал для task completion | `interactive` |
| `escalate_pressure` | повысить давление: ускорить речь, начать перебивать, повторить фразу | `interactive` |
| `end_call` | завершить звонок и закрыть обе сессии корректно | `hold` |

`tool.result` отправляется **только на `reply.done` со `status: "completed"`**, при `"interrupted"` очередь выбрасывается. `arguments` приходит объектом, `result` уходит **JSON-строкой** — асимметрия из [API AssemblyAI](../reference/assemblyai-api.md), самая частая ошибка. Модель LLM Gateway — из умеющих tool calling: `gemini-2.5-flash`, `gpt-5-mini`, `claude-haiku-4-5`. Дефолтный в примерах документации `qwen3.5-4b-32k-fast` tool calling **не умеет** — готовая ловушка и строка в README.

### Конфигурация наблюдателей (B и C)

```
speech_model=universal-3-5-pro
mode=max_accuracy            # наблюдателю латентность не важна, важна точность
format_turns=true
speaker_labels=true
language_codes=["en","es"]   # для code_switch; это bias, а не фильтр
session_heartbeat=true       # realtime_factor, max_speech_probability
encoding=pcm_mulaw&sample_rate=8000   # на профиле telephony_8k
```

Тонкость, которую надо назвать: на streaming параметр `speech_model` в **единственном** числе, на предзаписанном — `speech_models`. И `language_codes` **смещает** распознавание, но не блокирует неожидаемый язык.

`session_heartbeat` даёт `realtime_factor` — прямой индикатор, что наблюдатель не отстаёт от потока. Без него на профиле `burst` метрики молча поедут.

## 6. Что измеряем и как

### Определения

Метрика без определения — не метрика. Каждое определение здесь фиксировано до начала прогонов.

| Метрика | Определение |
|---|---|
| **Entity Error Rate** | Доля сущностей ground truth, не воспроизведённых целью корректно после нормализации. Считается **только по ходам, содержащим сущности**, не по всем ходам — прямо по их методологии. Нормализация: произнесённые цифры → цифры («four four seven one» → `4471`), регистр, пунктуация в пробелы |
| **Task completion rate** | Доля звонков, где все сущности сценария дошли до цели верно **и** цель выполнила ожидаемое действие (нужный `tool.call` с нужными аргументами или нужная фраза) |
| **Turn-to-turn latency** | От `input.speech.stopped` на стороне цели до первого байта её `reply.audio`, по монотонным часам. P50/P95/P99, не среднее |
| **Finalization delay** | От конца речи до `Turn` с `end_of_turn: true` — из наблюдателя, не из цели |
| **Barge-in rate** | Доля реплик цели, завершившихся `reply.done` со `status: "interrupted"`, ко всем её репликам |
| **Caller repeat rate** | Доля реплик звонящего, чей нормализованный текст совпадает с предыдущей его же репликой. Сегментировано по предшествующему вопросу цели |
| **Breach / degradation rate** | Доля прогонов сценария с провалом, **с интервалом Уилсона 95%** при N≥20. Wilson, а не нормальная аппроксимация: на малых N и долях у границы нормальная даёт интервалы, выходящие за [0,1] |
| **Cost per completed task** | Суммарное billable WebSocket-время × ставка / число успешных задач. Не $/час — их формулировка |

### Конструкция корпуса

По рекомендации AssemblyAI — не студийное аудио, а **50 худших звонков**: 8 kHz μ-law, фоновый шум, акценты, перебивания, фальстарты, высокая плотность сущностей.

Существенное преимущество конструкции Harness: **ground truth известен по построению, а не по ручной разметке.** Сущности генерирует инструмент `next_entity` звонящего — значит мы точно знаем, какая строка была произнесена, и не зависим от разметчика. AssemblyAI прямо предупреждает, что при ручной сверке «люди систематически теряют слова-заполнители и путают имена собственные». У нас этой проблемы нет на сущностях.

Что остаётся ручным и это надо признать: TTS звонящего произносит сущность, и произносит он её **не так, как человек**. Значит EER, измеренный через синтетического звонящего, — не оценка EER на живых звонках. Это **сравнительная** метрика: она валидна для сравнения конфигураций и целей между собой на одном стимуле, и невалидна как абсолютная оценка продакшн-качества. Это ограничение называется в README первой строкой, а не в подвале.

### Held-out дисциплина

Прямой обход слабости Saakshi (precision 1.00 на выборке 70 реплик, в которой они сами исправили 9 паттернов, и честно назвали это «regression suite, not a generalisation estimate»).

- Сценарии делятся на **dev** (на них настраиваем скорер, пейсер, деградатор) и **held-out** (размечаются в дни 1–2 и не запускаются ни разу до финальной оценки).
- Held-out прогоняется один раз, в конце, и число публикуется как есть — даже если оно хуже dev.
- Скорер детерминированный: тот же лог всегда даёт тот же вердикт. Стимул стохастичен, оценка — нет. Это правильное разделение, и его придумал Voxrede; мы его берём с атрибуцией.

### Что делает числа доказательными

1. **N ≥ 20 на сценарий с интервалом Уилсона.** Voxrede имеет n=2 и сам пишет, что находка — не оценка частоты. Мы делаем то, к чему он призывает.
2. **Разделение стабильных сценариев и флейков.** Сценарий, дающий провал в 18/20, и сценарий, дающий 2/20, — разные вещи, и отчёт их не смешивает.
3. **Прогон против не-своей цели.** Референсная цель — агент по официальному quickstart AssemblyAI без изменений. Промпт писали не мы.
4. **Публикация отрицательных результатов.** Если `telephony_8k` не даёт деградации — это публикуется, и это интересная находка, противоречащая ожиданию. Проект, публикующий свой отрицательный результат, читается как инструмент, а не как демо. Это тоже урок Voxrede.

### Наблюдаемость как страница продукта

Отдельная страница `/ledger`, не раздел в README:

- P50/P95/P99 по компонентам с порогами AssemblyAI рядом и цветовым вердиктом
- EER по типам сущностей (имена / места / телефоны / номера) — их разбивка 16,92% / 6,28% / 3,55% как референс
- caller repeat rate с разбивкой по предшествующему вопросу
- close codes **3007 / 3008 / 3009** с полным Error frame, а не обрезанной причиной закрытия
- billable-время, из него idle, cost per completed task
- `realtime_factor` из Heartbeat — доказательство, что наблюдатель не отставал

## 7. Демо для судьи

Судья один, времени мало, микрофона может не быть, ключа у него нет.

**Режим 1 — живой прогон.** Кнопка «Прогнать `entity_dense` против референсной цели, 3 звонка». Полностью серверный: судье микрофон не нужен вообще, потому что говорят два агента. На экране — таймлайн событий, два транскрипта, растущие счётчики. Это главное преимущество над Voxrede: у них демо — статический архив, а здесь кнопка.

**Режим 2 — judge-solo без ключа.** Тот же интерфейс, но проигрывается заранее записанный прогон из архива, событие за событием, в реальном темпе. Работает, если бэкенд лёг, если кредиты кончились, если у судьи нет интернета до AssemblyAI. Saakshi и Voxrede оба это предусмотрели, и оба правы.

**Режим 3 — сравнение.** Две цели рядом: агент по quickstart против того же агента с добавленным шагом подтверждения. Таблица дельт, интервалы Уилсона, и видно, что подтверждение поднимает completion и **платит за это латентностью**. Это A/B, воспроизводящий их 43,6% → 79,1% — на **не нашем** агенте.

### Про «навести Harness на публичное демо конкурента»

Заголовок «мы прогнали инструмент против демо другого сабмишена и вот его настоящие числа» — самая эффектная демонстрация, которую в этой нише можно сделать. И её делать нельзя. Разбор по частям:

| Аспект | Оценка |
|---|---|
| Технически | Возможно: у части сабмишенов публичные демо, WebSocket-эндпоинты доступны из браузера, токены минтятся их же бэкендом |
| Юридически | Автоматизированное нагрузочное и adversarial-тестирование чужого сервиса без письменного разрешения — это несанкционированное тестирование. Плюс сжигание чужих кредитов AssemblyAI: биллинг идёт по времени открытого WebSocket, то есть каждый наш звонок тратит **их** деньги. Плюс почти наверняка нарушение ToS их хостинга |
| Этически | Публикация измеренных слабостей конкурента, у которого нет возможности ответить, в соревновании, где мы с ним за один приз |
| Тактически | Худшее из всего. Судьи — сотрудники AssemblyAI. Инструмент, атакующий агентов на их API без согласия, читается как репутационный риск для организатора. Voxrede на этом уже получил замечание про «этическую мину», а он всего лишь опубликовал инструмент под MIT с оговоркой. Сделать это на сцене — гарантированный минус, который перекроет любой эффект |

**Безопасный вариант, дающий 90% эффекта:**

1. **Референсная цель — агент по официальному quickstart AssemblyAI, без изменений.** Промпт писали не мы, а организатор. Это полностью снимает главное возражение к Voxrede («тестирует свои фикстуры») и никого не задевает: мы тестируем документацию, а не участника.
2. **Вторая цель — наш собственный референсный агент** в двух версиях, base и hardened (с шагом подтверждения). Это даёт A/B.
3. **Opt-in для участников.** Публичная форма: «зарегистрируйте свой эндпоинт, получите отчёт». Кто согласился — того прогоняем и показываем результат **с его разрешения и его именем**. Это превращает потенциальный конфликт в сервис. Даже один согласившийся участник даёт заголовок «прогнано против внешнего агента с разрешения владельца».
4. **Механизм, а не оговорка.** Цель нельзя прогнать без записи в allowlist, а запись в allowlist требует токена, который бэкенд проверяет обратным вызовом на эндпоинт цели (владелец должен положить выданную строку по известному пути). Публичная сборка **не содержит телефонии** — дозвон на номер невозможен в принципе. Rate limit: не более N прогонов на цель в час. Всё это в коде и в тестах, а не в README.

Пункт 4 — прямое усиление относительно Voxrede: у них «point this only at agents you own» — оговорка. У нас — проверка владения, которую нельзя обойти, не переписав бэкенд.

| 0:00–0:15 | Проблема: EER 15,31% против WER 6,99%; 84,69% за ход → 43,6% за пять ходов |

Voxrede уже сдал такую конструкцию, и в разборе она названа сильнейшей стороной. Но если судья держит рамку «агент разговаривает с человеком», аргумента нет. ## 12. Что сказать в одном абзаце на питче

AssemblyAI 8 сентября опубликовала, что WER не работает как метрика приёмки голосового агента: у их собственной realtime-модели Entity Error Rate 15,31% при WER 6,99%, а при точности захвата сущностей 84,69% за один ход пятиходовое бронирование доходит до конца всего в 43,6% случаев — и вырастает до 79,1%, если добавить шаги подтверждения. Проблема в том, что проверить это на своём агенте нечем: цепочка STT→LLM→TTS не выдаёт сигнала ошибки, а LLM не может узнать, что его вход был неверным. Harness — голосовой агент, который звонит вашему голосовому агенту и проговаривает с ним враждебный сценарий: телефонные 8 kHz μ-law, шум, быстрая речь, перебивания посреди фразы, code-switched реплики, реплики с плотностью сущностей как в реальном заказе. Ground truth известен по построению, потому что сущности генерирует сам звонящий, а независимый Streaming STT слушает обе стороны и даёт `words[]` с таймкодами и уверенностью. На выходе — отчёт по той самой рамке, которую опубликовал вендор: Entity Error Rate по типам сущностей, P50/P95/P99 латентности по компонентам с их же порогами (finalization < 500 мс, time-to-first-audio P95 < 1500 мс), barge-in rate, caller repeat rate с разбивкой по вопросу агента, task completion rate с интервалом Уилсона на двадцати прогонах, и коды закрытия WebSocket 3007/3008/3009 вместе с billable-временем и idle. Прогнано против агента, собранного по официальному quickstart AssemblyAI — то есть против того, что построит средний разработчик по документации, а не против нашей собственной фикстуры.

## 13. Критическая самооценка

### Оценки по четырём критериям

| Критерий | Балл | Обоснование |
|---|---|---|
| **Application of Technology** | **9 / 10** | Сильнейшая сторона идеи, и здесь она бьёт RxGate. Три сокета одновременно: Voice Agent API как звонящий (tool calling, барж-ин, turn detection, `reply.done`-очередь) плюс два независимых Streaming STT v3 с `words[]`, `confidence`, `speaker_labels`, `format_turns`, `mode=max_accuracy`, `session_heartbeat`, `pcm_mulaw` на 8 kHz. Плюс LLM Gateway. Плюс работа с лимитами и close codes как с первоклассными объектами. Плюс воспроизведение close 3007 намеренно. Это ровно тот гибрид, который AssemblyAI назвала правильным («каскад отлаживается, чёрный ящик — нет»), и он задействует фичи, занятые 2–3 проектами из 45. Не 10 только потому, что Voxrede уже занял самое необычное применение (две сбриджованные Voice Agent сессии), и часть новизны придётся отдать с атрибуцией |
| **Presentation** | **6 / 10** | Слабое место, и это структурно. Живая кнопка бьёт статический архив Voxrede — это плюс. Таймлайн, двойной транскрипт, растущие счётчики, `/ledger` с порогами — инженерно красиво. Но сюжет — «два робота разговаривают, потом таблицы». Нет момента, который понятен не-инженеру за три секунды. У RxGate такой момент есть: агент отказывается оформить Bisoprolol вместо Lisinoprilа, и это понятно любому. Единственное сильное средство здесь — звук: дать услышать 8 kHz μ-law канал и сразу показать, как цель на нём ломается. Это поднимает до 7, если сделать хорошо, и не выше |
| **Business Value** | **5 / 10** | Самое слабое. Покупатель существует и реален — QA-команда, эксплуатирующая голосового агента; self-hosted аргумент для регулируемых отраслей работает. Но: бюджет на тестирование вторичен к бюджету на сам агент; ниша занята коммерчески (Bluejay, Coval, Hamming), и судья спросит, почему не купить готовое; и главное — нет числа, которое переводится в деньги одной строкой. У RxGate такое число есть готовое, от самой AssemblyAI: 43,6% → 79,1% успешных транзакций, что для колл-центра считается напрямую. Harness это число **измеряет на чужом агенте**, но сам его не создаёт. Разница между «мы почти удваиваем долю успешных транзакций» и «мы показываем, что у вас доля успешных транзакций 45%» — это разница между продуктом и отчётом |
| **Originality** | **5 / 10** | Честно низко. Ниша имеет прямого конкурента **внутри хакатона** (Voxrede, и он хорош), плюс занята коммерчески снаружи. Отличия Harness реальны и защитимы — непрерывные метрики вместо бинарных вердиктов, N≥20 с Уилсоном вместо n=2, глубина на уровне распознавателя, не-своя цель, живая кнопка — но это **другая ось того же продукта**, а не другой продукт. Судья, прочитавший оба сабмишена, увидит две работы про тестирование голосовых агентов. Единственный элемент, который читается как оригинальный сам по себе: звонящий, который генерирует ground truth через собственный tool call — то есть агент, знающий, что он сказал, точнее, чем любая разметка. Этого нет ни у Voxrede, ни в коммерческих продуктах |

**Сумма: 25 / 40.** Для сравнения, RxGate по той же шкале распределён ровнее: сравнимый Application of Technology (8–9: гибрид, word timings, `domain=medical-v1`, валидаторы с контрольными суммами), существенно выше Presentation (8–9: момент «поймай ошибку» понятен мгновенно) и Business Value (8–9: готовое число 43,6% → 79,1% как собственный эффект, регуляторный adversarial-набор от ISMP/FDA вместо самодельного), выше Originality (7–8: в нише приёма рецептов конкурентов внутри хакатона нет, ISMP-список как источник adversarial-корпуса не использовал никто).

### Когда Harness — лучший выбор, чем RxGate

1. **Если судьи от AssemblyAI весят больше, чем судьи от предприятий.** Из пяти инженерных судей организатора трое (Head of Realtime, PM, Forward Deployed Engineer) читают именно то, что Harness делает своим продуктом. Craig Bruder как Forward Deployed Engineer занимается ровно этим на работе — приходит к клиенту и выясняет, почему агент плохо работает. Harness — инструмент из его рабочего дня.
2. **Если нужен максимум по «Application of Technology» и остальное — как получится.** Три сокета, оба API, LLM Gateway, close codes, 8 kHz μ-law, диаризация, Heartbeat — по числу задействованных поверхностей Harness обходит всё поле.
3. **Если есть желание и запас времени на «подарок сообществу».** Harness естественно превращается в открытый инструмент, полезный любому, кто строит на AssemblyAI. Это то, что DevRel-судья (Harnoor Singh) может продвигать после хакатона. RxGate — вертикальный продукт, он так не переиспользуется.
4. **Если медицинская тема неприемлема.** RxGate требует дисциплины в дисклеймерах (Veritas на этом подставился, отключив safety-фильтры без медицинского дисклеймера). Harness от домена не зависит вообще.
5. **Если доступна хотя бы одна внешняя цель по opt-in.** Реальный прогон против чужого живого агента с разрешения владельца — заголовок, который бьёт всё поле и которого нет ни у кого, включая Voxrede.

### Когда Harness — хуже, чем RxGate

1. **Если призы распределяют по сумме четырёх критериев.** 25/40 против примерно 32/40. Два слабых критерия из четырёх — слишком дорого при пяти призовых местах.
2. **Если Voxrede дойдёт до финала.** Тогда два проекта в одной нише делят внимание, и сравнивать будут напрямую. У Voxrede 29 коммитов, CI, научная гигиена и лучший инсайт батча про пейсер. Выиграть у него можно, но это гонка внутри ниши вместо пустой ниши.
3. **Если судьи от предприятий (Amex, Prudential, Zocdoc, Meta, Amazon Ads) весят существенно.** Им нужна строка «это экономит столько». У RxGate она есть от вендора. У Harness её нет.
4. **Если времени меньше, чем 19 дней.** Критический путь Harness — двусторонний мост с пейсером между двумя сессиями Voice Agent API, и если он не заводится за два дня, проект рассыпается: остальное к нему пристёгнуто. RxGate деградирует плавно — можно резать шлюз, можно резать метрики, работающий голосовой приём данных остаётся демонстрируемым на любой стадии.
5. **Если важна убедительность демо для неинженера.** Таблицы против момента, где агент отказывается оформить не тот препарат, — проигрыш.
6. **Если нельзя обеспечить не-свою цель.** Без прогона против агента, написанного не нами, Harness наследует главную слабость Voxrede целиком, и тогда 25/40 превращается в существенно меньше.

### Гибридный вариант, который стоит рассмотреть отдельно

Технически можно взять RxGate как продукт и **встроить в него Harness как внутренний инструмент оценки**: тот же агент-звонящий с враждебными сценариями прогоняет RxGate, и страница `/metrics` RxGate наполняется числами, полученными именно так. Тогда:

- Business Value и Presentation берутся от RxGate (число 43,6% → 79,1% как собственный эффект, момент «поймай ошибку»);
- Application of Technology берётся от Harness (три сокета, 8 kHz μ-law, close codes, диаризация);
- Originality не страдает от близости Voxrede, потому что продукт — приём рецептов, а не тестирование.

Цена — объём: это два проекта за 19 дней. Реалистичная урезка: агент-звонящий **только** для генерации корпуса и замеров, без UI, без allowlist, без отчётов для внешних целей — то есть `scripts/` в RxGate, а не отдельный продукт. Это добавляет 2–3 дня к плану RxGate и закрывает два его слабых места сразу: корпус перестаёт быть синтезированным из WAV-файлов, а замеры латентности делаются живым разговором, а не проигрыванием.

**Это, вероятно, сильнейший вариант из трёх.** Но он требует, чтобы пейсер завёлся, и не должен угрожать ядру RxGate: если на дне 12 мост не работает, его вырезают, а корпус остаётся синтезированным — и проект не страдает.
